# 文档架构与维护规范

更新时间：2026-03-22 16:10:00 +08:00

## 1. 适用范围

本规范适用于：

- 根目录 `doc/`
- `common` 下的 `doc/`
- 所有子服务的 `doc/`
- 后续新增的跨服务功能主文档

## 2. 目标

本规范用于统一仓库文档的职责边界、目录结构、索引方式和设计落地方式，避免出现以下问题：

- 索引、设计、阶段说明、实施任务、历史记录混写
- 同一主题在多个位置重复展开正文
- 只有任务没有设计，或只有设计没有实施承接
- 文档链接依赖本机绝对路径，跨平台不可用
- 文档结构无法支撑后续持续维护

目标是让文档体系满足：

- 入口稳定
- 主文档唯一
- 上下游关系清晰
- 设计与实施分离
- 设计与任务可追踪
- 跨平台可打开

## 3. 总体原则

### 3.1 按范围分层

- 根目录 `doc/` 负责项目级、跨服务级、全局规范
- 子服务 `doc/` 负责服务级设计和本服务实施

### 3.2 按类型分槽

- `INDEX.md` 只做导航
- `overview.md` 只做高维说明
- `requirements.md` 只写实施约束
- `roadmap.md` 只写阶段说明
- `design/*.md` 只写稳定设计
- `tasks/*.md` 只写实施分片与状态
- `history/*.history.md` 只写历史记录

### 3.3 单一事实源

- 一个主题只能有一个主文档
- 其他文档只能引用，不能重复复制正文
- 历史文档不能替代当前有效设计

### 3.4 设计与实施分离

- `design` 回答“应该怎么设计”
- `tasks` 回答“接下来怎么落地”
- 任务推进时优先更新 `tasks`
- 只有设计本身变化时才更新 `design`

### 3.5 `design` 与 `tasks` 必须配对

- 存在实施意义的 `design/*.md` 必须明确列出“关联任务”
- `design` 不能停留在只讲方案、不指向落地分片的状态
- 如果当前尚无对应任务，必须明确标注“暂无实施分片”

### 3.6 `tasks` 默认按最小闭环切分

- `tasks/*.md` 默认以“单一功能分片 + 最小可验收闭环”为基本粒度
- 不应默认按大 Phase、大模块或大范围打包任务
- 如果某个任务包含多个独立功能，应优先继续拆分
- 任务命名应反映功能编号、功能点或明确业务分片

## 4. 根目录 `doc/` 要求

推荐结构：

```text
doc/
  INDEX.md
  overview.md
  standards/
  cross-service/
  history/
  archive/
```

各目录职责：

- `standards/`
  - 所有子服务共同遵循的全局规范
- `cross-service/`
  - 需要多个服务共同实现的跨服务功能主文档
- `history/`
  - 根目录文档的历史记录
- `archive/`
  - 旧方案、归档资料

根目录 `doc/` 不应承载：

- 单个子服务内部设计正文
- 单个子服务实施任务
- 单个服务自己的阶段状态

## 5. 子服务 `doc/` 要求

推荐结构：

```text
doc/
  INDEX.md
  overview.md
  requirements.md
  roadmap.md
  design/
  tasks/
  history/
```

各文件 / 目录职责：

- `INDEX.md`
  - 阅读入口
  - 当前有效主文档索引
  - 设计 / 任务 / 历史入口
- `overview.md`
  - 服务定位
  - 职责边界
  - 上下游依赖
- `requirements.md`
  - 本服务文档与实施约束
- `roadmap.md`
  - Phase 划分
  - 当前优先级
- `design/*.md`
  - 稳定设计正文
- `tasks/*.md`
  - 最小分片实施文档
- `history/*.history.md`
  - 历史记录

## 6. 索引要求

### 6.1 根目录 `INDEX.md`

必须包含：

- 文档职责说明
- 推荐阅读顺序
- `standards/` 入口
- `cross-service/` 入口
- 已有服务文档入口

不能承载：

- 完整设计正文
- 实施分片步骤
- 历史流水账

### 6.2 子服务 `INDEX.md`

必须包含：

- 服务文档定位说明
- 阅读顺序
- 基础文档入口
- 设计文档入口
- 任务文档入口
- 历史文档入口
- 与根目录全局规范的关联入口

### 6.3 索引链接要求

- 索引中的链接必须真实存在
- 优先链接当前有效主文档，不链接历史文档替代正文
- 如果列出跨服务能力，需同时给出根目录主文档和本服务承接文档入口

## 7. 文档类型要求

### 7.1 `overview.md`

建议包含：

- 服务 / 模块定位
- 负责什么
- 不负责什么
- 依赖哪些上游规范或文档
- 阅读方式

### 7.2 `requirements.md`

建议包含：

- 继承哪些全局规范
- 本服务额外执行约束
- 哪些变更必须先更新文档再改代码
- “已实现”状态判定规则

### 7.3 `roadmap.md`

建议包含：

- Phase 划分
- 每阶段目标
- 当前优先级
- 当前功能状态摘要

### 7.4 `design/*.md`

建议包含：

- 文档定位
- 目标
- 边界
- 设计决策
- 模型 / 流程 / 规则
- 长期注意事项
- 与其他设计文档的关系
- 关联任务与历史

强制要求：

- 每个 `design/*.md` 必须包含“关联任务”或等价小节
- 关联任务必须使用真实存在的文档链接
- 关联任务应优先按最小功能分片列出，而不是只链接阶段打包文档
- 如果一个设计对应多个任务，应按功能类别或实施顺序列出

### 7.5 `tasks/*.md`

建议包含：

- 上游设计文档
- 当前承接范围
- 当前状态
- 最小闭环范围
- 实施顺序
- 验收要求
- 阻塞项
- 关联设计文档

强制要求：

- 每个 `tasks/*.md` 必须明确指向上游 `design/*.md`
- 每个 `tasks/*.md` 应优先只承载一个最小功能闭环或一个明确子分片
- 如果任务范围较大，必须明确说明其最小闭环边界和不包含范围
- 不建议将多个独立功能合并成一个默认执行任务

### 7.6 `history/*.history.md`

建议包含：

- 本次目标
- 修改范围
- 主要改动
- 备注

历史文档不承担当前实现依据的角色。

## 8. 关联要求

### 8.1 根目录与子服务的关联

- 根目录文档负责全局规则和跨服务协作
- 子服务文档负责本服务如何落地
- 根目录可以索引子服务，但不复制子服务正文
- 子服务文档必须回链到相关根目录文档

### 8.2 设计文档之间的关联

- 如果一个设计依赖另一个设计，必须明确写出关系
- 如果一个设计只是某个跨服务功能在本服务内的承接，必须明确上游主文档
- 如果一个设计依赖其他领域设计能力，也应明确列出

### 8.3 任务文档与设计文档的关联

- 每个 `tasks/*.md` 都应明确指向上游 `design/*.md`
- 每个复杂设计文档都应尽量指出对应的实施文档
- 不能只存在任务文档而没有设计承接文档

追踪要求：

- `design -> tasks` 与 `tasks -> design` 应保持双向链接
- 如果 `task` 被拆分或重命名，对应 `design` 必须同步更新
- 如果 `design` 决策变化导致任务边界变化，相关 `tasks` 必须同步调整

## 9. 跨服务功能要求

跨服务功能不是协议附录，而是需要多个子服务共同实现的功能主文档。

推荐结构：

```text
doc/
  cross-service/
    <feature>.md

src/services/system/<service>/doc/
  design/
    <service-topic>.md
  tasks/
    <feature>.md
```

职责分工：

- 根目录 `cross-service/<feature>.md`
  - 总设计
  - 总拆分
  - 全局职责边界
  - 分片编号
- 服务内 `design/*.md`
  - 该功能在本服务内如何承接
  - 本服务设计边界与设计映射
- 服务内 `tasks/<feature>.md`
  - 本服务按什么顺序落地
  - 当前状态和验收要求

强制要求：

- 不能只建跨服务主文档，不建子服务承接文档
- 不能只建子服务任务文档，不建子服务设计承接文档

## 10. 编号与状态要求

### 10.1 功能编号

所有稳定功能集合和核心功能项都应编号，便于：

- 索引引用
- 任务拆分
- 历史追踪

### 10.2 状态枚举

统一使用：

- `未开始`
- `部分实现`
- `已实现`

### 10.3 “已实现”判定

至少应满足：

- 设计与代码一致
- 文档已更新
- 必要验证已完成
- 不存在明显未闭合边界

## 11. 链接与兼容性要求

由于开发环境存在 Windows 和 macOS，文档链接必须遵循：

- 一律使用仓库相对路径
- 不写本机绝对路径
- 索引和正文都应可在不同系统打开

适用范围：

- 根目录文档
- 子服务文档
- 历史文档
- Markdown 表格中的链接

## 12. 命名要求

### 12.1 目录命名

推荐使用语义稳定的目录名：

- `standards`
- `cross-service`
- `design`
- `tasks`
- `history`
- `archive`

避免使用长期含义不清的目录名，例如：

- `func`
- `misc`
- `tmp`
- `final`

### 12.2 文件命名

文件名应按“主题”命名，而不是按“版本形容词”命名。

推荐：

- `authorization.md`
- `role-management.md`
- `internal-service-auth-and-operator-context.md`

不推荐：

- `最终版.md`
- `完整方案.md`
- `优化版.md`

## 13. 维护要求

### 13.1 变更顺序

推荐顺序：

1. 先确认是否需要更新根目录规范或跨服务主文档
2. 再更新服务内设计文档
3. 再更新任务文档
4. 最后补历史记录

### 13.2 何时更新 `design`

当以下内容变化时，应更新 `design`：

- 目标变化
- 边界变化
- 模型变化
- 流程变化
- 长期约束变化

### 13.3 何时更新 `tasks`

当以下内容变化时，应更新 `tasks`：

- 当前状态
- 实施顺序
- 验收条件
- 阻塞项
- 任务拆分边界

### 13.4 何时更新 `history`

当以下内容发生时，应更新 `history`：

- 文档结构调整
- 设计决策变化
- 重要实现方式变化
- 链接或目录迁移

## 14. 对后续线程的直接要求

后续任何线程在创建或调整文档时，应默认遵循本规范：

- 先判断这是全局规范、跨服务功能，还是子服务内部文档
- 先判断这是索引、设计、任务还是历史
- 先找主文档，避免重复创建
- 修改链接时始终保持相对路径
- 若文档职责不清，优先整理结构，再继续写正文
