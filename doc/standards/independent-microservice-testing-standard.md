# 独立微服务测试标准

更新时间：2026-03-22 12:35:00 +08:00

## 1. 适用范围

本标准适用于 OES 仓库中的独立微服务，优先覆盖：

- `permission-service`
- `auth-service`
- `identity-service`
- 其他后续新增的 system / business / auxiliary 子服务

本标准只关注单个服务自身的可靠性验证，不覆盖整个平台联调，不要求同时启动全部微服务。

## 2. 标准目标

本标准统一回答四个问题：

1. 当前服务的核心业务规则是否正确
2. 当前服务自己的数据库行为是否正确
3. 当前服务对外提供的接口是否正确
4. 当前服务改动后是否破坏了已有能力

本标准强调两个结果：

- 测试目标要清楚，业务方能看懂“在验证什么”
- 测试结果要清楚，业务方能看懂“通过了什么，失败了什么”

## 3. 测试边界

### 3.1 本标准覆盖

- 单个服务内部的业务规则
- 单个服务自己的持久化层
- 单个服务自己的接口层
- 单个服务以接近真实方式启动后的关键主流程

### 3.2 本标准不覆盖

- 多个微服务一起联调
- 网关到下游整链路系统测试
- 跨服务事务一致性测试
- 前端到后端的端到端测试
- 全平台压测、容量测试、灾备测试

### 3.3 独立测试边界原则

- 本服务拥有的数据和存储，优先使用真实依赖
- 外部微服务、第三方接口、基础设施平台能力，优先使用替身
- 不允许为了测试单个服务而要求整个平台一起启动

具体执行规则：

- 本服务自己的数据库：使用真实测试库
- 本服务关键缓存存储：可使用真实测试缓存，也可在第一阶段先用替身
- Nacos、注册中心、服务发现：测试中禁用
- 外部微服务调用：使用 mock、fake adaptor 或 stub server
- 短信、邮件、第三方 API：使用 stub，不调用真实外部系统

## 4. 测试分层标准

所有独立微服务统一采用四层测试模型。

### 4.1 L1 业务规则测试

目的：

- 验证纯业务逻辑是否正确
- 快速发现规则回归

特点：

- 不连接数据库
- 不连接外部服务
- 执行速度最快
- 适合作为每次改动后的第一道反馈

主要对象：

- domain service
- aggregate
- value object
- command handler
- query handler
- validator
- mapper 中的纯规则逻辑

结论标准：

- 能直接回答“规则对不对”

### 4.2 L2 服务内集成测试

目的：

- 验证本服务代码与本服务数据库协同时是否正确

特点：

- 连接真实测试数据库
- 不连接其他微服务
- 重点验证 repository、schema、事务与约束

主要对象：

- Prisma repository
- 事务逻辑
- 唯一约束
- 外键或关联约束
- 分页、过滤、排序查询

结论标准：

- 能直接回答“数据落库和取数是否正确”

### 4.3 L3 接口契约测试

目的：

- 验证本服务对外接口的结构、映射和错误码是否正确

特点：

- 只启动当前服务
- 不依赖整个平台运行
- 重点检查 controller、DTO、mapper、proto 或请求响应结构

主要对象：

- gRPC controller
- TCP controller
- HTTP controller
- request / response mapper
- proto / DTO / exception mapping

结论标准：

- 能直接回答“外部调用方能否按约定正确调用本服务”

### 4.4 L4 服务级冒烟测试

目的：

- 验证服务能够以接近真实方式启动，并完成少量关键主流程

特点：

- 只保留少量高价值场景
- 不追求覆盖全面
- 用于确认服务未出现整体不可用问题

主要对象：

- 创建
- 查询
- 更新
- 删除
- 鉴权
- 登录
- 账号管理

结论标准：

- 能直接回答“服务是否还活着，主路径是否可用”

## 5. 统一目录规范

所有服务的测试文件统一放在服务根目录下的 `test` 目录中，不允许将测试文件分散放在 `src/**/*.spec.ts`。

推荐结构：

```text
src/services/system/<service>/
  src/
  test/
    l1/
    l2/
    l3/
    l4/
    fixtures/
    helpers/
  package.json
```

各目录职责：

- `test/l1/`
  - 业务规则测试
- `test/l2/`
  - 服务内集成测试
- `test/l3/`
  - 接口契约测试
- `test/l4/`
  - 服务级冒烟测试
- `test/fixtures/`
  - 测试数据、假对象、固定请求体
- `test/helpers/`
  - 测试工厂、环境启动器、数据库清理工具

命名建议：

- `*.spec.ts` 保持通用测试入口
- 文件名尽量体现对象和层级

例如：

- `test/l1/policy-engine.spec.ts`
- `test/l1/create-permission.handler.spec.ts`
- `test/l2/prisma.permission.repository.spec.ts`
- `test/l3/permission-management.grpc.spec.ts`
- `test/l4/permission-service.smoke.spec.ts`

## 6. 统一命名规范

每条测试用例统一采用：

`对象 / 场景 / 期望结果`

示例：

- `创建权限 / 当 code 已存在时 / 应返回 PERMISSION_ALREADY_EXISTS`
- `权限判断 / 当命中 DENY policy 时 / 应返回 false`
- `删除权限 / 当权限仍被角色引用时 / 应拒绝删除`

要求：

- 用业务语言命名
- 不使用模糊命名，如 `should work`
- 测试名称必须让非测试背景人员也能看懂

## 7. 统一执行策略

### 7.1 默认执行顺序

每个服务统一按以下顺序执行：

1. L1 业务规则测试
2. L2 服务内集成测试
3. L3 接口契约测试
4. L4 服务级冒烟测试

原因：

- 先用最快的测试发现纯逻辑问题
- 再验证数据库和接口
- 最后验证服务整体主路径

### 7.2 提交前最低要求

每次改动至少满足：

- 涉及业务规则变更时，必须新增或更新 L1
- 涉及数据库查询、事务、约束变更时，必须新增或更新 L2
- 涉及对外接口、DTO、proto 变更时，必须新增或更新 L3
- 核心主流程变更时，必须确认对应 L4 未失效

### 7.3 修复缺陷要求

每次修 bug 必须新增一条能够复现该问题的测试，再修复代码。

禁止：

- 只改代码不补测试
- 只补 happy path，不补失败路径

## 8. 统一结果输出规范

每次执行测试后，结果必须能够被非测试背景人员直接阅读。

统一输出为三部分。

### 8.1 测试摘要

必须包含：

- 服务名称
- 执行时间
- 测试范围
- 总数
- 通过数
- 失败数

示例：

```text
服务：permission-service
时间：2026-03-22 14:00:00 +08:00
范围：L1 + L2
总数：18
通过：16
失败：2
```

### 8.2 失败清单

每条失败至少包含：

- 测试名称
- 期望结果
- 实际结果
- 初步原因

示例：

```text
1. 删除权限 / 当权限仍被角色引用时 / 应拒绝删除
   期望：返回 PERMISSION_DELETE_FORBIDDEN
   实际：删除成功
   初步原因：删除前未检查 RolePermission 关联
```

### 8.3 覆盖说明

必须用业务语言说明：

- 本次已覆盖哪些能力
- 本次未覆盖哪些能力
- 当前剩余主要风险是什么

禁止只给一个覆盖率百分比而不解释业务范围。

## 9. 通用验收门槛

单个服务测试通过的最低标准：

- L1 必须全部通过
- L2 中核心 repository 必须通过
- L3 中核心对外接口必须通过
- L4 至少覆盖 3 到 5 条关键主路径

阶段性验收可采用以下结论：

- `可接受`
  - 核心能力已覆盖，未覆盖部分不影响当前上线范围
- `有风险`
  - 核心能力存在失败用例，或关键能力尚未覆盖
- `不可接受`
  - 核心业务规则、数据库约束或主路径未通过

## 10. permission-service 首期落地标准

`permission-service` 作为本标准的第一个样板服务，优先覆盖权限、角色、策略、鉴权四类能力。

### 10.1 首期测试目标

先回答以下问题：

1. 权限创建、更新、删除的规则是否正确
2. 权限与角色、策略的关联约束是否正确
3. 权限判断逻辑是否正确
4. 服务接口是否能正确暴露这些能力

### 10.2 首期测试清单

#### L1 业务规则测试

优先用例：

1. 创建权限 / 当 code 不存在时 / 应创建成功
2. 创建权限 / 当 code 已存在时 / 应返回 `PERMISSION_ALREADY_EXISTS`
3. 查询权限 / 当按 id 查询且存在时 / 应返回权限详情
4. 查询权限 / 当按 id 查询但不存在时 / 应返回 `PERMISSION_NOT_FOUND`
5. 更新权限 / 当修改 description 时 / 应更新成功
6. 删除权限 / 当未被引用时 / 应删除成功
7. 删除权限 / 当仍被角色引用时 / 应返回 `PERMISSION_DELETE_FORBIDDEN`
8. 删除权限 / 当仍被 policy 引用时 / 应返回 `PERMISSION_DELETE_FORBIDDEN`
9. 权限判断 / 当 RBAC 允许且无 policy 时 / 应返回 `true`
10. 权限判断 / 当命中 DENY policy 时 / 应返回 `false`
11. 权限判断 / 当命中 ALLOW policy 时 / 应返回 `true`
12. 权限判断 / 当存在 policy 但没有 ALLOW 命中时 / 应返回 `false`
13. 权限判断 / 当 tenantId 不匹配时 / 应忽略该 policy
14. 权限判断 / 当 resourceType 不匹配时 / 应忽略该 policy
15. 权限判断 / 当 condition AST 非法时 / 应返回 `false`

建议优先覆盖的代码对象：

- `PolicyEngine`
- `CheckPermissionHandler`
- `CreatePermissionHandler`
- `DeletePermissionHandler`
- `UpdatePermissionHandler`

#### L2 服务内集成测试

优先用例：

1. Permission 仓储 / 当保存新权限时 / 应正确落库
2. Permission 仓储 / 当插入重复 code 时 / 应触发唯一约束失败
3. RolePermission 仓储 / 当插入重复关系时 / 应触发唯一约束失败
4. Policy 仓储 / 当 permissionCode 无效时 / 应拒绝保存
5. 权限分页查询 / 当按 module 过滤时 / 应返回正确结果
6. 权限分页查询 / 当按 keyword 过滤时 / 应返回正确结果
7. 删除权限前检查 / 当存在角色关联时 / 应识别为禁止删除
8. 删除权限前检查 / 当存在 policy 关联时 / 应识别为禁止删除

#### L3 接口契约测试

优先用例：

1. gRPC 创建权限 / 当请求合法时 / 应返回成功响应
2. gRPC 创建权限 / 当 code 重复时 / 应返回预期异常码
3. gRPC 查询权限 / 当权限存在时 / 应返回详情
4. gRPC 查询权限 / 当权限不存在时 / 应返回预期异常码
5. gRPC 分页查询权限 / 当分页参数有效时 / 应返回正确分页结构
6. gRPC 检查权限 / 当命中拒绝策略时 / 应返回拒绝结果

#### L4 服务级冒烟测试

首期只保留以下主路径：

1. 创建权限 -> 查询权限
2. 给角色分配权限 -> 检查权限
3. 给权限绑定 policy -> 再次检查权限

### 10.3 permission-service 首期验收结论标准

若以下条件同时满足，可判定为首期测试方案通过：

- 15 条 L1 用例全部通过
- 8 条 L2 用例全部通过
- 6 条 L3 用例全部通过
- 3 条 L4 冒烟用例全部通过

若未全部满足，则在测试报告中按以下方式标记：

- 核心风险
- 非核心待补项
- 是否阻断当前阶段交付

## 11. 向 auth-service 和 identity-service 复用的规则

后续迁移到其他服务时，不复用具体业务用例，复用的是测试骨架。

可复用内容：

- 四层测试模型
- `test/l1` 到 `test/l4` 的目录规则
- 测试命名方式
- 测试结果输出方式
- 缺陷补测试规则
- 最低验收门槛

迁移时只替换业务对象：

- `permission-service`
  - 权限、角色、策略、鉴权
- `auth-service`
  - 登录、会话、MFA、token、登出
- `identity-service`
  - 账号、资料、状态、唯一性、组织归属

## 12. 实施顺序建议

建议采用统一的落地顺序：

1. 先建立服务级 `test/` 目录骨架
2. 先补 L1 业务规则测试
3. 再补 L2 服务内集成测试
4. 再补 L3 接口契约测试
5. 最后补少量 L4 冒烟测试
6. 形成第一版测试报告模板

不建议一开始就直接写大量接口级冒烟测试，否则维护成本会很高，定位问题也会变差。

## 13. 最终结论

OES 独立微服务测试标准的核心不是“把所有测试都写出来”，而是统一建立一套团队可复用、业务可阅读、结果可判断的验证机制。

对所有独立服务，统一要求：

- 测试文件全部放在服务根目录 `test/`
- 单个服务按 L1、L2、L3、L4 四层执行
- 命名必须让非测试背景人员可读
- 输出必须明确展示测试目标与测试结果
- `permission-service` 先作为样板服务落地，再推广到 `auth-service`、`identity-service`
