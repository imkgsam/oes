# OES 文档体系概览

更新时间：2026-03-22 12:00:00 +08:00

## 目标

当前文档体系主要服务两类读者：

- Codex：快速定位当前有效设计、全局约束和服务级落地入口
- 人工维护者：查看项目边界、设计决策、阶段推进和历史演进

因此文档结构采用“按范围分层，按类型分槽”的轻量规则，避免一个文档同时承担索引、设计、计划、进度和注意事项。

## 根目录 `doc` 的职责

根目录 `doc` 只放以下内容：

- 项目级说明和总索引
- 适用于整个仓库的执行约束
- 跨服务架构与协议
- 从已实现服务中提炼出的可复用架构规范
- 历史项目资料归档

根目录 `doc` 不承担以下内容：

- 单个子服务内部设计细节
- 单个子服务的实现步骤和待办拆分
- 单个功能的长期正文说明

## 子服务 `doc` 的职责

每个子服务自己的 `doc/` 负责：

- 说明该服务的定位、边界、依赖关系
- 维护该服务内的功能设计正文
- 维护该服务的阶段路线和实现任务
- 记录该服务自己的历史变更

## 推荐文档类型

### `INDEX.md`

只做导航：

- 先看什么
- 当前有效主文档是哪篇
- 哪些文档属于设计、任务、历史

### `overview.md`

写高维说明：

- 服务或模块是干什么的
- 边界是什么
- 依赖谁
- 当前能力域有哪些

### `design/*.md`

写稳定设计：

- 设计目标
- 设计决策
- 核心模型
- 核心流程
- 长期约束与注意事项

### `tasks/*.md` 或 `roadmap.md`

写高频变化内容：

- 当前阶段
- 分片实施步骤
- 待办与验收标准
- 阻塞项

### `history/*.history.md`

只记录演进历史，不承载当前设计结论。

## 根目录与子服务的关系

- 根目录文档负责“全局规则”和“跨服务协作”
- 子服务文档负责“本服务如何落地”
- 根目录可以索引子服务，但不重复拷贝正文
- 子服务文档需要回链到相关全局文档，说明自己受哪些全局约束约束

## 跨平台链接规则

为了兼容 Windows 和 macOS：

- 索引文档统一使用相对路径链接
- 不在仓库文档中写本机绝对路径
- 目录命名和链接目标以仓库相对位置为准
