

## 1. 背景

在 OES 系统中，用户或服务的每一次请求都需要经过以下授权流程：

- **身份验证**：通过 JWT 校验用户或服务身份
    
- **权限校验**：确认请求方是否具备调用目标模块的权限
    
- **Scope 校验**：资源级权限控制，确认请求方是否有权访问或操作指定资源
    

原高安全方案流程中：

1. 用户请求 → API Gateway → 子模块
    
2. 子模块每次 RPC 调用 `permission-service` 查询权限
    
3. 子模块再执行 scope 校验
    

**问题**：

- 每次请求都触发网络调用 + DB 查询 → 延迟高
    
- permission-service 成为潜在性能瓶颈
    
- 故障传播风险大
    
- 子模块之间多层 RPC 调用导致请求链路延长，系统可扩展性受限
    

---

## 2. 优化目标

- **保持高安全性**：身份验证 + 权限 + scope 校验不变
    
- **减少请求延迟**：避免每次 RPC 调用 permission-service
    
- **提升系统可扩展性**：降低 permission-service 的压力
    
- **支持内部服务、机器人服务、APIKey 调用**
    

---

## 3. 核心原则

1. **身份验证集中、鉴权决策分散**
    
    - JWT 用于验证身份（签名、有效期、issuer、audience）
        
    - 权限与 Scope 校验在各子模块本地完成
        
2. **权限数据集中管理，最终裁决分布式执行**
    
    - `permission-service` 作为权限与角色的 **Source of Truth**
        
    - 权限和角色的变更通过事件驱动方式分发到各子模块
        
    - 子模块本地维护缓存，实现最终鉴权
        
3. **事件驱动 + 本地缓存**
    
    - 子模块订阅 `permission-service` 发布的事件：
        
        - RolePermissionChanged
            
        - AccountRoleChanged
            
    - 更新本地缓存，不依赖实时 RPC
        

---

## 4. 请求处理流程

### 4.1 用户请求流程（高安全 + 性能优化）

`用户/外部服务 → API Gateway       |       |-- JWT 验证（身份验证）       |-- APIKey 或 Endpoint 粗粒度权限过滤       v   子模块（业务服务）       |       |-- JWT 验签（轻量）       |-- 本地权限缓存查 Role → Permission       |-- Scope 校验（资源边界）       |-- 执行业务逻辑       v   返回结果`

- **JWT 校验**：确保请求身份真实
    
- **本地权限缓存 + Scope 校验**：做最终裁决
    
- **RPC 调用 permission-service 仅用于**：
    
    - 初始化缓存
        
    - 事件驱动更新
        

---

### 4.2 事件驱动权限同步

- `permission-service` 发布权限变更事件
    
- 子模块订阅事件 → 更新本地缓存
    
- 可选：定期拉取权限快照，确保缓存一致性
    

---

## 5. 子模块本地缓存设计

- **缓存类型**：
    
    - 内存缓存或 Redis
        
    - 按 Tenant/Role 分段存储
        
    - 仅存角色 → Permission 映射，不展开到每个用户
        
- **缓存更新策略**：
    
    - 事件驱动更新（实时或近实时）
        
    - 定期快照同步（防止事件丢失）
        
- **Scope 校验**：
    
    - 每个业务模块负责自身资源边界
        
    - 与请求参数绑定，例如资源ID、Tenant、Org
        

---

## 6. 性能分析（典型场景对比）

假设单个子模块处理请求：

|方案|JWT 验签|权限查询|Scope 校验|总额外延迟|
|---|---|---|---|---|
|原方案：每次 RPC permission-service|10ms|60ms|5ms|75ms|
|优化方案：本地缓存 + 事件驱动|10ms|1~2ms|5ms|16~17ms|

**多层子模块调用链（3层）**：

- 原方案总延迟：≈ 225ms
    
- 优化方案总延迟：≈ 48~50ms
    
- **性能提升约 3~4 倍**
    

---

## 7. 安全性分析

- JWT 校验确保身份真实性
    
- 本地缓存 + Scope 校验确保权限和资源边界裁决
    
- 权限变更通过事件同步，保持最终一致性
    
- 内部服务、机器人服务、APIKey 调用无需经过 Gateway，也保持安全
    

---

## 8. 风险与注意点

1. **缓存一致性**：
    
    - 事件延迟或丢失 → 权限变更可能短暂失效
        
    - 建议关键权限操作可短期触发 token / 缓存刷新
        
2. **缓存容量**：
    
    - 用户、角色、权限量大 → Redis / 内存管理需优化
        
    - 可用 TTL / LRU 策略
        
3. **系统复杂度**：
    
    - 子模块维护本地缓存 + 事件订阅逻辑
        
    - 需要确保事件安全、可靠、顺序一致
        

---

## 9. 总结

> **方案核心**：JWT 验证轻量化 + 权限/Scope 本地缓存 + 事件驱动更新  
> **优势**：高安全性、低延迟、可扩展性强、系统可靠性高  
> **适用场景**：OES 全量微服务架构、支持 Gateway、内部服务和机器人服务调用
