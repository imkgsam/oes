# OES 文档架构规范

## 1. 目的

本文档定义 OES 项目的最终文档架构，目标是：

- 保持单一真相源
- 降低 Codex thread 的最小阅读成本
- 避免多份文档重复描述同一件事
- 让计划、契约、架构、协作状态各归其位

本文档是文档治理基线，服从以下上游规则：

- `AGENTS.md`
- `docs/architecture/*.md`
- `docs/adr/*.md`

## 2. 第一原则

OES 文档系统的第一原则是：

- 单一真相源优先

这意味着：

- 同一条稳定设计只允许有一个正式归属位置
- 其他文档只能引用，不能再次解释为第二份真相
- 文档数量本身不是问题，职责重叠才是问题

## 2.1 默认执行倾向

为避免文档系统不断膨胀、thread 读入过多上下文，默认再补充以下执行倾向：

- 优先代码推进，文档只做必要回写
- 优先冻结“当前阶段最小真相”，而不是一次性写全量设计
- 优先让文档回答“去哪里看”，而不是在多份文档重复解释同一件事
- 优先用短结构化条目维护状态，不写大段重复背景
- checklist 只做状态板，不做需求、架构或契约真相源

只有当边界、契约、协作方式或后置判断发生变化时，才应新增或明显扩写文档正文。

## 3. 最终分层

OES 文档默认分为六类真相源与协作层：

### 3.1 `docs/architecture/`

职责：

- 项目级稳定设计
- 长期边界
- 职责划分
- 明确禁止事项

只回答：

- 系统边界是什么
- 长期模型是什么
- 哪些职责归谁
- 哪些做法禁止
- 某项服务职责或协同规则最终应落到哪里

不负责：

- 当前执行状态
- feature 级协作记录
- checklist
- backlog 收集

### 3.2 `docs/architecture/services/`

职责：

- 单个服务的长期职责卡
- 服务负责什么 / 不负责什么
- 服务拥有哪些核心能力与主数据事实

只回答：

- 这个服务长期负责什么
- 这个服务不应承担什么
- 它向外提供哪些能力真相

不负责：

- feature 执行状态
- 详细接口字段
- 大段跨服务协同流程正文

### 3.3 `docs/architecture/collaborations/`

职责：

- 关键跨服务能力的协同蓝图
- 多个服务围绕一项能力如何配合

只回答：

- 这个能力由哪些服务参与
- 每个服务在该能力中负责什么
- 哪些步骤走同步调用，哪些走事件

不负责：

- 单个服务完整职责卡
- feature 执行状态
- 契约字段正文

### 3.4 `docs/contracts/`

职责：

- 黑盒契约
- request / response
- error semantics
- fixture / example payload
- 当前是否已实现

只回答：

- 外部或下游应如何调用
- 返回什么
- 错误语义是什么

不负责：

- 宏观架构论证
- 执行拆分
- feature 状态同步

### 3.5 `docs/plans/`

职责：

- 阶段推进
- 实施切片
- feature 协作面板
- ideas / candidates / backlog

只回答：

- 当前阶段怎么推进
- 当前 feature 由谁推进
- 哪些内容尚未进入实现
- 哪些事项明确后置
- 当前 feature 依赖哪些服务职责与协同蓝图

不负责：

- 长期稳定架构真相
- 黑盒契约正文
- 服务职责真相
- 可复用的跨服务协同规则正文

### 3.6 `docs/governance/`

职责：

- 多线程协作规则
- 文档规则
- 计划、审核、集成纪律
- 疑难 bug 根因知识库与防复发规则

只回答：

- thread 怎么拆
- 谁能改什么
- 文档怎么归位
- feature packet 怎么使用
- 哪些疑难 bug 根因值得跨线程复用

不负责：

- feature 本身设计
- 具体实现状态

## 4. 文档类型与归属

### 4.1 `index`

允许长期存在。

职责：

- 纯导航
- 告诉阅读者去哪里看

约束：

- 不承载大段设计正文
- 不承载执行状态真相

### 4.2 `summary / overview`

允许存在，但不是默认必需。

职责：

- 作为压缩入口，帮助快速进入上下文

约束：

- 不能成为第二份设计说明
- 不能重复契约正文
- 不能重复执行状态正文

只有当导航价值明显高于重复成本时，才允许保留。

### 4.3 `backlog`

允许长期存在。

职责：

- 只收“已确认后置事项”与“从活跃 feature 派生、但当前不做的 sidecar work”

不再承担：

- 灵感池
- 候选功能池
- 当前活跃 feature 的 blocker

结构要求：

- 不允许把所有后置事项混在同一张未分类列表中
- `backlog.md` 必须按“为什么后置、何时解除后置”进行分类
- 默认采用以下分层：
  - `Platform Deferred`
  - `Product Deferred`
  - `Operational Deferred`
  - `Extraction Deferred`
  - `Sidecar Work`

分类含义：

- `Platform Deferred`
  - 跨服务的平台基础能力、治理能力、平台化能力
- `Product Deferred`
  - 明确有价值但当前不进入主线的产品能力
- `Operational Deferred`
  - 生产化、运营化、可观测性、安全分析等后置治理项
- `Extraction Deferred`
  - 当前已有样板，但尚不适合立即抽象成共享模型或共享模块的事项
- `Sidecar Work`
  - 从活跃 feature 派生，但当前不进入主线的问题或无关工作

维护要求：

- 新条目写入 backlog 时，必须先确定所属分类
- 如无法判断分类，不应直接入 backlog，应先回到 `ideas` / `candidates` / `feature packet`
- backlog thread 在统计或回写条目时，不得打破该分类结构
- backlog thread 在写入新条目前，必须先做重复检查，避免把同一事项以不同表述重复登记
- 如发现已有同类条目，应优先更新原条目的“当前判断 / 触发条件 / 目标落点”，而不是新增重复条目

### 4.4 `feature packet`

允许长期作为模板与活跃 feature 面板存在。

职责：

- 当前跨线程 feature 的唯一协作状态真相
- 当前 feature 依赖哪些上游服务职责文档、协同蓝图与 contracts

不负责：

- 稳定架构真相
- 服务长期职责真相
- 可复用的跨服务协同规则
- 黑盒契约真相
- backlog 收集

### 4.5 `knowledge base / lessons learned`

允许长期存在，但应严格控制范围。

职责：

- 记录已经完成根因分析、且值得跨线程复用的疑难 bug 总结
- 沉淀防复发规则、排查入口与归位规则

不负责：

- 普通 feature 历史流水账
- 单次联调过程全文
- 尚未确认根因的猜测性记录

约束：

- 必须以“问题现象 -> 根本原因 -> 正式修复 -> 防复发规则”为主结构
- 若结论已经上升为稳定架构规则，应链接到对应 `docs/architecture/*.md`
- 若只是单服务实现收尾记录，应留在服务内 `doc/history/*.history.md`

## 5. ideas / candidates / backlog / feature packet 分层

为避免把“灵感、候选功能、后置事项、派生问题”混在一起，统一采用以下分层：

### 5.1 `ideas.md`

作用：

- 记录随时出现的灵感
- 目标是防遗忘，不要求已经想清楚

进入条件：

- 值得记住
- 但尚未准备进入设计

报告要求：

- 当用户要求输出 `idea` 报告时，应优先给出简洁概览
- 默认展示：
  - 当前总数
  - 每条 idea 的简短列表
- 报告目标是帮助用户快速扫描并挑选下一步想推进的事项
- 除非用户继续追问，不应默认展开长篇背景说明

### 5.2 `candidates.md`

作用：

- 记录明确值得推进，但尚未完成设计的候选功能或候选设计议题

进入条件：

- 用户明确想做
- 但边界、契约、实施方式还没定

报告要求：

- 当用户要求输出 `candidate` 报告时，应优先给出简洁概览
- 默认展示：
  - 当前总数
  - 每条 candidate 的简短列表
  - 必要时补一列当前判断或下一步
- 报告目标是帮助用户快速识别值得升级为正式 plan 的候选项
- 除非用户继续追问，不应默认展开长篇设计分析

### 5.3 `backlog.md`

作用：

- 记录已确认后置事项
- 记录从活跃 feature 派生，但当前不做的 sidecar / unrelated work

约束：

- 必须按分类分段维护，不得退化为单一混合列表
- 每个条目都应能回答：
  - 为什么现在不做
  - 何时触发重新评估
  - 重新评估后应迁向哪里
- 新条目写入前必须先查重；若 backlog 中已存在同一任务，应更新原条目，不得重复新增

### 5.4 `features/<feature-key>.md`

作用：

- 记录当前活跃 feature 的主线范围、owner、slice、阻塞、派生问题和关闭条件
- 引用当前 feature 所依赖的服务职责文档、协同蓝图与 contracts

报告要求：

- 当用户要求输出 `feature` 报告时，应优先给出简洁概览
- 默认展示：
  - 当前 feature 总数
  - 每个 feature 的简短列表
  - 必要时补充状态字段，如 `active / paused / completed`
- 报告目标是帮助用户快速从 feature 列表中挑选想继续推进的一项
- 除非用户继续追问，不应默认把每个 feature 的上下文全文展开

### 5.5 判断规则

当新增一条内容时，按以下规则归位：

- “先记住，别忘了” -> `ideas.md`
- “这个值得做，但还没设计完” -> `candidates.md`
- “这个确定要做，但不是现在” -> `backlog.md`
- “这是当前活跃 feature 推进中发现的问题” -> 当前 `feature packet`

## 6. 单一真相源规则

### 6.1 稳定设计

稳定设计只能归属：

- `docs/architecture/**`
- 或 `docs/adr/**`

### 6.2 契约真相

契约真相只能归属：

- `docs/contracts/**`

### 6.3 服务职责真相

服务职责真相只能归属：

- `docs/architecture/services/*.md`

每个服务只能有一个稳定设计真相源文件：

- 文件位置固定为 `docs/architecture/services/<service-name>.md`
- 服务长期边界、核心对象、对象命名、拥有与不拥有的真相只能在该文件中定义
- 其他服务文档、design workspace、feature packet、collaboration、contract 或实现说明可以描述“如何依赖该服务”，但不得重新定义该服务的领域对象或形成第二份设计真相
- 其他文档引用服务对象时，必须以服务真相源为依据；如果需要展开说明，应链接对应服务真相源，而不是复制一份解释
- 若其他文档与服务真相源冲突，默认以服务真相源为准，并应把冲突内容改成引用、降级为历史说明或删除
- 若需要改变服务边界或对象命名，必须先更新对应服务真相源；跨服务协同变化再同步更新 `docs/architecture/collaborations/*.md`，关键取舍再补 ADR

### 6.4 协同真相

跨服务协同真相只能归属：

- `docs/architecture/collaborations/*.md`

### 6.5 当前协作状态

当前协作状态只能归属：

- `docs/plans/features/<feature-key>.md`

### 6.6 后置与收集

未进入当前活跃实现的想法和事项，只能归属：

- `ideas.md`
- `candidates.md`
- `backlog.md`

### 6.7 疑难 bug 根因总结

跨线程可复用、且已经完成根因分析的疑难 bug 总结，归属：

- `docs/governance/tricky-bug-knowledge-base.md`

普通服务实现历史、阶段收尾记录不应挤占该入口，仍应归属服务内 `doc/history/*.history.md`

## 7. 生命周期规则

### 7.1 什么时候保留文档

一份文档只有在以下情况之一成立时才应保留：

- 它是正式真相源
- 它是必要导航
- 它是当前活跃协作面板
- 它是必要的收集入口

### 7.2 什么时候降级

当一份文档不再是正式真相源，但仍有导航价值时：

- 将其降级为 index / summary / redirect 文档

### 7.3 什么时候清理正文

当一份文档已经被正式真相源完全覆盖，且不再承担导航价值时：

- 清理正文
- 保留必要引用
- 或直接删除

## 7.4 文档最小化规则

为了让项目长期保持“少而准”，默认执行以下最小化规则：

- 一个活跃 feature 默认只依赖一份 feature packet 作为执行真相
- 一个接口能力默认只依赖一份 contracts 文档作为黑盒真相
- 一个稳定边界默认只依赖一份 architecture / ADR 文档作为设计真相
- 不为“解释已有解释”新增 overview / summary 文档
- 如某份 summary 无法提供明确导航价值，应优先删减而不是继续扩写

默认情况下，thread 开工前真正需要阅读的核心材料应压缩为：

1. `AGENTS.md`
2. 必要的 architecture / ADR
3. 当前 feature packet
4. 当前相关 contracts
5. 自己负责路径下的代码

## 8. 对 thread 的最小阅读要求

设计文档架构的目标之一，是让 thread 默认只读最小必需集。

默认推荐顺序：

1. `AGENTS.md`
2. 必要的项目级 architecture / ADR
3. 对应服务职责文档
4. 对应协同蓝图
5. 对应 feature packet
6. 对应 contracts
7. 自己负责路径下的代码

如果一个 thread 需要阅读大量横向摘要文档才能开始工作，说明文档系统已经偏离本规范。

## 8.1 需求到实现的最小闭环

为降低“先做后端，再迁就前端”或“先做前端，再倒逼后端”带来的反复摇摆，默认采用以下最小闭环：

1. 先确认业务场景或用户目标
2. 再确定页面 / 交互或消费方真正需要的能力
3. 再冻结该阶段的最小黑盒契约
4. 最后进入 producer / consumer 的实现拆分

这里冻结的不是永久真理，而是当前阶段允许并行推进的工作基线。

换句话说：

- 前端不应以“现有后端已经这么写了”作为唯一真相
- 后端也不应以“现有前端暂时能凑合”作为唯一真相
- 双方都应围绕已冻结的当前黑盒契约推进

## 8.2 变更分类与回写规则

当实现过程中发现“冻结过早”或“需求发生变化”时，不允许直接在 thread 中无边界漂移，必须先判断变化类型：

### `Implementation Adjustment`

含义：

- 不改变用户目标
- 不改变黑盒契约
- 只是实现细节、内部结构、测试、性能或局部行为调整

处理方式：

- 直接在当前实现 thread 中处理
- 不回写 architecture / contracts / feature packet 真相
- 如会影响进度判断，可只更新 feature packet 的状态说明

### `Contract Revision`

含义：

- 用户目标不变
- 但 request / response / error semantics / fixture 发生变化

处理方式：

- 先更新 `docs/contracts/**`
- 再同步受影响的 producer / consumer 实现
- 再在 feature packet 中更新当前 slice 判断

### `Feature Revision`

含义：

- 目标、范围、边界、验收标准或“不做什么”发生变化

处理方式：

- 先回写当前 `feature packet`
- 如已触及稳定边界，再升级到 architecture / ADR
- 再重新判断 thread 分工、slice 与主线范围

总规则：

- 冻结的是当前阶段工作基线，不是永久不可变真相
- 任何变化都必须先判断属于实现调整、契约修订还是 feature 修订
- 然后回写到对应真相源，而不是在多个文档里各写一份解释

## 9. 新服务与新协同模式的准入规则

当目标包含以下任一情况时，不能只写 feature packet：

- 新增服务，例如 `erp-service`
- 明确调整某服务长期职责边界
- 引入新的跨服务协同模式
- 某段说明预计会被两个以上 feature 复用

此时默认顺序应为：

1. 必要时先更新项目级 architecture 或 ADR
2. 补对应服务职责文档
3. 补对应协同蓝图
4. 补 contracts
5. 最后进入 `candidates` 或 `feature packet`
