# OES 文档架构规范

## 1. 目的

本文档定义 OES 项目的最终文档架构，目标是：

- 保持单一真相源
- 降低 Codex thread 的最小阅读成本
- 避免多份文档重复描述同一件事
- 让计划、契约、架构、协作状态各归其位

本文档是文档治理基线，服从以下上游规则：

- `AGENTS.md`
- `docs/architecture/*.md`
- `docs/adr/*.md`

## 2. 第一原则

OES 文档系统的第一原则是：

- 单一真相源优先

这意味着：

- 同一条稳定设计只允许有一个正式归属位置
- 其他文档只能引用，不能再次解释为第二份真相
- 文档数量本身不是问题，职责重叠才是问题

## 3. 最终分层

OES 文档默认分为四层：

### 3.1 `docs/architecture/`

职责：

- 项目级稳定设计
- 长期边界
- 职责划分
- 明确禁止事项

只回答：

- 系统边界是什么
- 长期模型是什么
- 哪些职责归谁
- 哪些做法禁止

不负责：

- 当前执行状态
- feature 级协作记录
- checklist
- backlog 收集

### 3.2 `docs/contracts/`

职责：

- 黑盒契约
- request / response
- error semantics
- fixture / example payload
- 当前是否已实现

只回答：

- 外部或下游应如何调用
- 返回什么
- 错误语义是什么

不负责：

- 宏观架构论证
- 执行拆分
- feature 状态同步

### 3.3 `docs/plans/`

职责：

- 阶段推进
- 实施切片
- feature 协作面板
- ideas / candidates / backlog

只回答：

- 当前阶段怎么推进
- 当前 feature 由谁推进
- 哪些内容尚未进入实现
- 哪些事项明确后置

不负责：

- 长期稳定架构真相
- 黑盒契约正文

### 3.4 `docs/governance/`

职责：

- 多线程协作规则
- 文档规则
- 计划、审核、集成纪律

只回答：

- thread 怎么拆
- 谁能改什么
- 文档怎么归位
- feature packet 怎么使用

不负责：

- feature 本身设计
- 具体实现状态

## 4. 文档类型与归属

### 4.1 `index`

允许长期存在。

职责：

- 纯导航
- 告诉阅读者去哪里看

约束：

- 不承载大段设计正文
- 不承载执行状态真相

### 4.2 `summary / overview`

允许存在，但不是默认必需。

职责：

- 作为压缩入口，帮助快速进入上下文

约束：

- 不能成为第二份设计说明
- 不能重复契约正文
- 不能重复执行状态正文

只有当导航价值明显高于重复成本时，才允许保留。

### 4.3 `backlog`

允许长期存在。

职责：

- 只收“已确认后置事项”与“从活跃 feature 派生、但当前不做的 sidecar work”

不再承担：

- 灵感池
- 候选功能池
- 当前活跃 feature 的 blocker

### 4.4 `feature packet`

允许长期作为模板与活跃 feature 面板存在。

职责：

- 当前跨线程 feature 的唯一协作状态真相

不负责：

- 稳定架构真相
- 黑盒契约真相
- backlog 收集

## 5. ideas / candidates / backlog / feature packet 分层

为避免把“灵感、候选功能、后置事项、派生问题”混在一起，统一采用以下分层：

### 5.1 `ideas.md`

作用：

- 记录随时出现的灵感
- 目标是防遗忘，不要求已经想清楚

进入条件：

- 值得记住
- 但尚未准备进入设计

### 5.2 `candidates.md`

作用：

- 记录明确值得推进，但尚未完成设计的候选功能或候选设计议题

进入条件：

- 用户明确想做
- 但边界、契约、实施方式还没定

### 5.3 `backlog.md`

作用：

- 记录已确认后置事项
- 记录从活跃 feature 派生，但当前不做的 sidecar / unrelated work

### 5.4 `features/<feature-key>.md`

作用：

- 记录当前活跃 feature 的主线范围、owner、slice、阻塞、派生问题和关闭条件

### 5.5 判断规则

当新增一条内容时，按以下规则归位：

- “先记住，别忘了” -> `ideas.md`
- “这个值得做，但还没设计完” -> `candidates.md`
- “这个确定要做，但不是现在” -> `backlog.md`
- “这是当前活跃 feature 推进中发现的问题” -> 当前 `feature packet`

## 6. 单一真相源规则

### 6.1 稳定设计

稳定设计只能归属：

- `docs/architecture/**`
- 或 `docs/adr/**`

### 6.2 契约真相

契约真相只能归属：

- `docs/contracts/**`

### 6.3 当前协作状态

当前协作状态只能归属：

- `docs/plans/features/<feature-key>.md`

### 6.4 后置与收集

未进入当前活跃实现的想法和事项，只能归属：

- `ideas.md`
- `candidates.md`
- `backlog.md`

## 7. 生命周期规则

### 7.1 什么时候保留文档

一份文档只有在以下情况之一成立时才应保留：

- 它是正式真相源
- 它是必要导航
- 它是当前活跃协作面板
- 它是必要的收集入口

### 7.2 什么时候降级

当一份文档不再是正式真相源，但仍有导航价值时：

- 将其降级为 index / summary / redirect 文档

### 7.3 什么时候清理正文

当一份文档已经被正式真相源完全覆盖，且不再承担导航价值时：

- 清理正文
- 保留必要引用
- 或直接删除

## 8. 对 thread 的最小阅读要求

设计文档架构的目标之一，是让 thread 默认只读最小必需集。

默认推荐顺序：

1. `AGENTS.md`
2. 对应 feature packet
3. 对应 contracts
4. 必要的 architecture
5. 自己负责路径下的代码

如果一个 thread 需要阅读大量横向摘要文档才能开始工作，说明文档系统已经偏离本规范。
