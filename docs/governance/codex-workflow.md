# OES Codex 标准工作流

## 1. 目的

本文档定义 OES 项目中 Codex 多线程协作的标准执行流程。

目标是让每一轮开发都遵循统一步骤，避免：

- 先实现后发现边界未定
- 线程并行但互相覆盖文件
- 审核与集成顺序混乱

对跨前后端或跨服务 feature，除本工作流外，还应同时遵循：

- `docs/governance/codex-feature-threading.md`
- `docs/governance/docs-architecture.md`
- `docs/governance/execution-complexity.md`

其中定义了 feature packet、thread 生命周期、owner 分工与 vertical slice 拆分规则。

## 2. 标准开发流程

### 第一步：plan thread

职责：

- 基于已有架构与治理文档理解目标
- 判断是单模块变更、跨模块变更还是架构级变更
- 判断当前 feature 的执行复杂度
- 判断是否涉及新增服务职责或新增协同模式
- 将目标拆成可执行任务
- 如果是跨线程 feature，先建立 `docs/plans/features/<feature-key>.md`

输入：

- `AGENTS.md`
- `docs/architecture/**`
- `docs/governance/**`
- 已有 ADR
- 当前需求

输出：

- 任务拆分清单
- 串行与并行边界
- 每个线程的允许修改路径
- 每个任务的输入、输出、验收标准
- 如涉及新服务或新协同模式，先补服务职责文档与协同蓝图
- 如果需要跨线程协作，还应产出 feature packet
- 如果是跨线程 feature，还应明确是否必须先有 design thread

验收标准：

- 每个任务边界清晰
- 没有两个 implementation thread 共享同一批核心文件
- 所有跨模块改动已被识别
- 若存在服务职责变更或协同模式变更，已识别其唯一真相源落点

### 第二步：拆分任务

职责：

- 将任务分配到具体线程类型
- 明确每个线程的 ownership

输入：

- 计划线程输出

输出：

- 线程清单
- 每个线程的 prompt 输入材料
- 每个线程的路径边界
- 需要引用的服务职责文档、协同蓝图与 contracts

验收标准：

- 每个线程的职责单一
- 每个线程的输入文档完整
- 没有未定义 ownership 的高风险文件

### 第三步：implementation threads 并行执行

职责：

- 在冻结边界内完成局部实现

输入：

- 线程专属任务说明
- 上游设计文档
- 允许修改路径

输出：

- 局部实现结果
- 验证结果
- 风险说明

验收标准：

- 未越界修改受保护文件
- 未扩大任务范围
- 输出与计划线程定义一致

### 第四步：review thread

职责：

- 对实现结果做结构化审核

输入：

- implementation thread 结果
- 上游架构和计划文档

输出：

- 审核结论
- 问题清单
- 是否允许进入集成

验收标准：

- 已检查边界破坏
- 已检查契约风险
- 已检查验证是否充分

### 第五步：integration thread

职责：

- 合并已审核通过的结果
- 处理兼容问题与收口

输入：

- 通过 review 的多个结果
- 集成顺序说明

输出：

- 集成后的统一结果
- 冲突消解说明
- 最终验证结果

验收标准：

- 无未决冲突
- 无受保护边界被意外改写
- 集成后结构仍符合既有架构文档

## 3. 每一步的输入/输出汇总

### 3.1 plan thread

输入：

- 架构基线
- 治理规则
- 需求目标

输出：

- 拆分方案
- 路径边界
- 验收标准

### 3.2 任务拆分

输入：

- 拆分方案

输出：

- 线程分配与 ownership

### 3.3 implementation threads

输入：

- 明确范围
- 上游文档
- 路径限制

输出：

- 局部修改结果

### 3.4 review thread

输入：

- 局部修改结果
- 上游基线

输出：

- review 结论

### 3.5 integration thread

输入：

- review 通过的修改

输出：

- 集成结果

## 4. 失败回滚策略

### 4.1 计划阶段失败

当 plan thread 无法清晰拆分任务时：

- 停止并行
- 回退到 architecture thread 明确边界
- 在边界明确前不启动 implementation thread

### 4.2 实现阶段偏离设计

当 implementation thread 出现以下情况时，必须停止：

- 修改了未授权路径
- 发现必须更改共享契约
- 设计含义不清
- 文档不清晰或与当前实现明显冲突
- 任务范围需要扩大才能继续
- 无法保证改动后的系统可构建或可运行
- 需要改变租户、权限、AI、operator context 语义

处理方式：

- 回退到 plan 或 architecture thread
- 不允许继续扩展实现

### 4.3 审核阶段不通过

当 review thread 判定存在架构破坏、契约风险、验证不足时：

- 退回原 implementation thread 修正
- 不得跳过 review 直接集成

### 4.4 集成阶段发现冲突

当 integration thread 发现多个线程结果冲突时：

- 先按计划边界判断 ownership
- 如果冲突属于架构/契约层面，升级为 architecture thread 处理
- 如果冲突属于实现层面，退回相关 implementation thread 收敛

## 5. 工作流执行纪律

- 先计划，后实现
- 先定服务职责与协同真相，再推进依赖它们的 feature 实现
- 先审核，后集成
- 任何跨模块边界问题优先升级，而不是在实现线程内临时拍板
- 分片只有在代码、契约、数据和文档边界均闭合，并完成必要验证后，才能标记为“已实现”
- 若未执行 build / test / 联调验证，输出中必须明确说明原因和剩余风险
- 未完成全链路闭环的功能只能标记为“部分实现”，不得用局部通过替代完成态
- 普通实现线程不得通过“顺手修一下”修改受保护文件
- 新增服务或新增长期协同模式时，默认先补 `docs/architecture/services/*.md` 与 `docs/architecture/collaborations/*.md`，再进入 `candidates` 或 `feature packet`

### 5.1 缺陷修复与代码质量纪律

所有线程在修复缺陷时必须先完成根因分析，再进入实现。

强制流程：

1. 复现或确认问题现象。
2. 找出根本原因，明确直接症状与真实原因的区别。
3. 给出正式解决方案，并说明其边界、影响范围与验证方式。
4. 再进行代码修改。
5. 完成后验证根因已消除，而不只是当前案例暂时通过。

禁止行为：

- 不允许用临时兜底、硬编码、特殊分支掩盖真实问题。
- 不允许在未确认根因时进行大范围试错式修改。
- 不允许交付短期能跑、长期需要推倒重来的低质量实现。
- 不允许把应在公共契约、基础设施、领域模型中修复的问题转移到调用方反复补丁。

实现要求：

- 使用最少、最聚焦、最符合既有架构边界的代码改动。
- 优先采用成熟、可维护、可测试、符合最佳实践的方案。
- 如果根因指向架构、契约、共享抽象或跨线程边界，应先升级治理流程，再继续实现。
- 如因联调阻塞必须临时止血，必须显式标记为临时方案，并记录正式修复路径与移除条件。

## 6. 服务级验证分层

单个服务的验证优先按以下层次选择，不要求为了验证一个服务而启动整个平台：

- L1 业务规则测试：覆盖 aggregate、domain service、command / query handler、validator、mapper 中的纯业务规则
- L2 服务内集成测试：覆盖本服务数据库、repository、事务、唯一约束、分页与过滤
- L3 接口契约测试：覆盖 gRPC / HTTP controller、DTO、proto 映射与异常转换
- L4 服务级冒烟测试：覆盖少量关键主流程，确认服务可启动且主路径可用

验证边界：

- 本服务拥有的数据存储优先使用真实测试依赖
- 外部微服务、第三方 provider、注册中心和平台基础设施优先使用 mock、fake adaptor 或 stub
- 不允许为了单服务验证而要求全平台同时启动

验证选择：

- 业务规则变化应优先补充或更新 L1
- 数据库查询、事务或约束变化应优先补充或更新 L2
- 对外接口、DTO、proto 或错误映射变化应优先补充或更新 L3
- 核心主流程变化应确认对应 L4 未失效
- 修复缺陷时，应优先新增能够复现该问题的测试，再修复代码

## 7. 结论

OES 的标准工作流本质上是：

- 用 plan thread 控制任务边界
- 用 implementation threads 提高并行度
- 用 review thread 控制质量
- 用 integration thread 控制最终一致性

这个顺序不可反转，也不应被省略。
