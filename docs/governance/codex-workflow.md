# OES Codex 标准工作流

## 1. 目的

本文档定义 OES 项目中 Codex 多线程协作的标准执行流程。

目标是让每一轮开发都遵循统一步骤，避免：

- 先实现后发现边界未定
- 线程并行但互相覆盖文件
- 审核与集成顺序混乱

## 2. 标准开发流程

### 第一步：plan thread

职责：

- 基于已有架构与治理文档理解目标
- 判断是单模块变更、跨模块变更还是架构级变更
- 将目标拆成可执行任务

输入：

- `AGENTS.md`
- `docs/architecture/**`
- `docs/governance/**`
- 已有 ADR
- 当前需求

输出：

- 任务拆分清单
- 串行与并行边界
- 每个线程的允许修改路径
- 每个任务的输入、输出、验收标准

验收标准：

- 每个任务边界清晰
- 没有两个 implementation thread 共享同一批核心文件
- 所有跨模块改动已被识别

### 第二步：拆分任务

职责：

- 将任务分配到具体线程类型
- 明确每个线程的 ownership

输入：

- 计划线程输出

输出：

- 线程清单
- 每个线程的 prompt 输入材料
- 每个线程的路径边界

验收标准：

- 每个线程的职责单一
- 每个线程的输入文档完整
- 没有未定义 ownership 的高风险文件

### 第三步：implementation threads 并行执行

职责：

- 在冻结边界内完成局部实现

输入：

- 线程专属任务说明
- 上游设计文档
- 允许修改路径

输出：

- 局部实现结果
- 验证结果
- 风险说明

验收标准：

- 未越界修改受保护文件
- 未扩大任务范围
- 输出与计划线程定义一致

### 第四步：review thread

职责：

- 对实现结果做结构化审核

输入：

- implementation thread 结果
- 上游架构和计划文档

输出：

- 审核结论
- 问题清单
- 是否允许进入集成

验收标准：

- 已检查边界破坏
- 已检查契约风险
- 已检查验证是否充分

### 第五步：integration thread

职责：

- 合并已审核通过的结果
- 处理兼容问题与收口

输入：

- 通过 review 的多个结果
- 集成顺序说明

输出：

- 集成后的统一结果
- 冲突消解说明
- 最终验证结果

验收标准：

- 无未决冲突
- 无受保护边界被意外改写
- 集成后结构仍符合既有架构文档

## 3. 每一步的输入/输出汇总

### 3.1 plan thread

输入：

- 架构基线
- 治理规则
- 需求目标

输出：

- 拆分方案
- 路径边界
- 验收标准

### 3.2 任务拆分

输入：

- 拆分方案

输出：

- 线程分配与 ownership

### 3.3 implementation threads

输入：

- 明确范围
- 上游文档
- 路径限制

输出：

- 局部修改结果

### 3.4 review thread

输入：

- 局部修改结果
- 上游基线

输出：

- review 结论

### 3.5 integration thread

输入：

- review 通过的修改

输出：

- 集成结果

## 4. 失败回滚策略

### 4.1 计划阶段失败

当 plan thread 无法清晰拆分任务时：

- 停止并行
- 回退到 architecture thread 明确边界
- 在边界明确前不启动 implementation thread

### 4.2 实现阶段偏离设计

当 implementation thread 出现以下情况时，必须停止：

- 修改了未授权路径
- 发现必须更改共享契约
- 设计含义不清
- 需要改变租户、权限、AI、operator context 语义

处理方式：

- 回退到 plan 或 architecture thread
- 不允许继续扩展实现

### 4.3 审核阶段不通过

当 review thread 判定存在架构破坏、契约风险、验证不足时：

- 退回原 implementation thread 修正
- 不得跳过 review 直接集成

### 4.4 集成阶段发现冲突

当 integration thread 发现多个线程结果冲突时：

- 先按计划边界判断 ownership
- 如果冲突属于架构/契约层面，升级为 architecture thread 处理
- 如果冲突属于实现层面，退回相关 implementation thread 收敛

## 5. 工作流执行纪律

- 先计划，后实现
- 先审核，后集成
- 任何跨模块边界问题优先升级，而不是在实现线程内临时拍板
- 普通实现线程不得通过“顺手修一下”修改受保护文件

## 6. 结论

OES 的标准工作流本质上是：

- 用 plan thread 控制任务边界
- 用 implementation threads 提高并行度
- 用 review thread 控制质量
- 用 integration thread 控制最终一致性

这个顺序不可反转，也不应被省略。
