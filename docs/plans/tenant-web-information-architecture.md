# OES Tenant Web 信息架构设计

更新时间：2026-04-09 21:10:00 +08:00

## 1. 文档目的

本文档定义 `tenant-web` 的产品级信息架构，用于指导：

- 一级导航与二级模块划分
- 默认工作台与首页结构
- 哪些内容属于稳定壳层
- 哪些内容属于后续逐步接入的业务域能力

本文档的目标不是一次性穷举所有 ERP / MES / WMS 页面，而是先建立一个可长期扩展、不需要后期推翻的前端骨架。

## 2. 设计原则

### 2.1 先稳定壳层，再逐步接入业务域

`tenant-web` 当前面对的现实是：

- 平台基础能力与 IAM 仍在建设中
- 业务域服务尚未全面落地
- 前端不能按“已有后端页面需求”倒推出结构

因此，信息架构必须先冻结稳定骨架，再允许业务域分阶段填充。

### 2.2 按工作场景组织，而不是按服务名组织

前端一级导航不应直接等同于后端服务名。

例如：

- 前端可以有“采购协同”
- 后端仍然可能由 `procurement-service`、`workflow-service`、`notification-service` 等共同支撑

这符合 OES 的 bounded context 原则，也更符合真实用户的使用方式。

### 2.3 终端准入与业务权限分离

信息架构必须允许：

- 某个用户可以登录 `tenant-web`
- 但只能看到其中一部分导航与页面

因此：

- “是否允许进入 tenant-web” 是终端准入
- “进入后能看到哪些模块和操作” 是菜单 / 页面 / 按钮权限摘要

### 2.4 支持未来多业务域接入，不要求现在全部实现

当前信息架构需要为以下业务域预留稳定位置：

- ERP / Finance
- WMS / Inventory
- MES / Manufacturing
- APS / Planning
- CRM / SRM
- Workflow / Task
- Reporting / BI

但不要求当前阶段全部展开为可访问页面。

## 3. tenant-web 的定位

`tenant-web` 是面向租户内办公、管理与业务操作岗位的统一 Web 前端。

当前承载范围：

- 租户治理
- 办公协同
- 报表与工作台
- 业务域操作入口
- 业务域配置入口

当前不承载范围：

- 平台级治理控制台
- PDA / 现场作业端
- Windows 工位终端
- 微信小程序
- 外部客户 / 供应商协同前端

## 4. 顶层信息架构

### 4.1 一级导航建议

建议 `tenant-web` 的一级导航稳定为以下七组：

1. 工作台
2. 协同与待办
3. 主数据与组织
4. 经营与交易
5. 供应链与库存
6. 制造与计划
7. 分析与治理

这七组不是“当前都要上线”，而是稳定骨架。

### 4.2 为什么这样分

这种分组方式有几个好处：

- 对最终用户更自然，按工作任务而不是按服务内部边界理解系统
- 能覆盖 OES 后续主要业务域
- 不会因为某个服务未来拆分或合并而推翻前端导航
- 允许当前只落少量模块，后续逐步填充

## 5. 一级导航详解

### 5.1 工作台

定位：

- 租户内用户进入系统后的默认首页
- 展示个人、岗位、组织、业务汇总信息

建议二级模块：

- 我的工作台
- 常用入口
- 最近访问
- 预警摘要
- 快速发起

当前优先级：

- 最高

说明：

- 这是当前最适合先落地的模块
- 即使业务域未完全接入，也可以先承载待办、通知、快捷入口和系统摘要

### 5.2 协同与待办

定位：

- 承载所有跨业务域的个人协同入口

建议二级模块：

- 待办中心
- 我发起的流程
- 我参与的审批
- 通知中心
- 消息与提醒

说明：

- 这组能力不应深度绑定某一个业务域
- 它是 `tenant-web` 的横向工作流入口

### 5.3 主数据与组织

定位：

- 承载租户治理与租户内基础配置

建议二级模块：

- 租户资料
- 组织与部门
- 岗位与成员
- 账号与身份
- 角色与授权
- 终端准入
- 参数配置

说明：

- 这是当前阶段最适合与系统能力一起先落的模块组
- 其本质是租户内治理，而不是平台治理

### 5.4 经营与交易

定位：

- 承载面向订单、客户、采购、财务等办公业务流程的入口

建议二级模块：

- 客户与销售
- 采购协同
- 订单与合同
- 财务与结算
- 售后与服务

说明：

- 这是“ERP 风格”能力的主要入口组
- 当前阶段可以只先保留入口，不展开全部页面

### 5.5 供应链与库存

定位：

- 承载库存、仓储、入出库、批次与物流相关能力

建议二级模块：

- 库存总览
- 仓储执行
- 入库
- 出库
- 调拨
- 批次与追溯

说明：

- 这组后续会承接 WMS 方向能力
- 与“经营与交易”分开，可以避免后续库存能力做大后重新洗牌

### 5.6 制造与计划

定位：

- 承载生产执行与计划调度相关能力

建议二级模块：

- 生产看板
- 工单与工序
- 报工与质检
- 计划排程
- 产能与约束

说明：

- 当前阶段大概率不会完整落地
- 但必须在顶层结构中预留稳定位置，否则未来 MES / APS 接入时会冲击整个导航

### 5.7 分析与治理

定位：

- 承载报表、仪表盘、审计、告警和系统级可视化能力

建议二级模块：

- 经营分析
- 运营报表
- 审计与留痕
- 风险与预警
- 系统运行概览

说明：

- 这里的“治理”指租户内运行治理，不是平台治理
- 平台级监控与运维治理仍属于 `platform-web`

## 6. 默认首页设计

### 6.1 默认首页原则

默认首页建议固定为：

- `工作台 / 我的工作台`

不建议：

- 以某个业务域首页作为默认首页
- 以纯菜单列表作为默认首页

原因：

- `tenant-web` 面向的是多岗位统一入口
- 业务域成熟速度不同，工作台更适合作为中性入口

### 6.2 工作台建议结构

建议工作台固定包含以下区域：

1. 当前上下文区
   - 当前租户
   - 当前组织
   - 当前身份 / 岗位
2. 待办区
   - 审批
   - 待处理任务
   - 风险提醒
3. 快捷入口区
   - 常用模块
   - 最近访问
4. 经营摘要区
   - 订单
   - 采购
   - 库存
   - 生产
5. 通知区
   - 系统通知
   - 业务提醒

当前阶段允许只先实现：

- 上下文区
- 快捷入口区
- 简单通知区

## 7. 导航生成策略

### 7.1 哪些导航应由前端固定维护

以下内容建议由前端固定维护：

- 根路由
- 登录 / 认证路由
- 404 / 403 / 错误页
- 工作台骨架页
- 壳层菜单分组的稳定标识

### 7.2 哪些导航应由后端摘要驱动

以下内容建议由 BFF / Gateway 返回摘要驱动：

- 用户实际可见的一二级菜单
- 菜单排序
- 默认首页候选
- 页面可见性
- 按钮 / 操作码摘要

### 7.3 为什么不把所有导航全交给后端

如果把整套路由完全交给后端，风险是：

- 前端壳层稳定性变差
- 页面资产与路由资产耦合过深
- 本地开发和重构成本上升

如果把所有导航都固定在前端，风险是：

- 无法体现租户、角色、终端差异
- 权限摘要无法自然落地

因此建议采用“前端固定骨架 + 后端返回可见性摘要”的混合模式。

## 8. 模块接入顺序建议

### 8.1 第一阶段

建议优先落地：

- 工作台
- 协同与待办
- 主数据与组织

原因：

- 与当前系统能力建设最贴近
- 对业务域成熟度依赖最低
- 能尽早把 tenant context、account context、role context 跑通

### 8.2 第二阶段

建议逐步接入：

- 经营与交易
- 供应链与库存

原因：

- 这两组更容易形成从订单到库存的主链路闭环

### 8.3 第三阶段

建议后续接入：

- 制造与计划
- 分析与治理增强能力

原因：

- MES / APS 往往更依赖前面业务链路与主数据成熟度

## 9. 当前阶段不建议做的事

- 不建议现在就把一级导航细化成最终几十个菜单项
- 不建议按后端服务名直接生成前端导航
- 不建议为了当前只有系统能力，就把 `tenant-web` 限缩成“系统设置后台”
- 不建议把 `tenant-web` 再拆成多个租户侧 Web

## 10. 本文档输出的可执行结论

当前可以直接作为后续实现依据的结论：

- `tenant-web` 的默认首页是工作台
- 一级导航稳定为七组
- 当前第一批优先建设工作台、协同与待办、主数据与组织
- 后续业务域按“经营与交易 -> 供应链与库存 -> 制造与计划”逐步接入
- 导航采用“前端固定骨架 + 后端返回可见性摘要”的混合模式
