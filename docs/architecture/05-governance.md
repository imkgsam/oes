# OES 治理规则

## 1. 治理目标

治理的目标不是增加流程，而是在多人、多线程、长期演进的前提下，让 OES 保持：

- 结构一致
- 边界清晰
- 责任明确
- 变更可控
- 设计可追踪

OES 是一个会持续扩大的企业级平台，没有治理就无法稳定演进。

## 2. 全项目统一设计原则

- 边界清晰优先于局部复用。
- 平台能力统一建设，业务能力领域化建设。
- 微服务拆分节制，避免过度拆分。
- 共享库只放通用能力，不放跨域业务逻辑。
- 所有跨模块协作都必须通过显式契约与文档表达。
- AI 增强必须服从业务边界与安全治理。

## 3. 模块间协作规则

### 3.1 协作方式

模块之间应通过以下方式协作：

- gRPC 契约
- 领域事件
- 防腐层
- 文档化的上下文关系

### 3.2 禁止事项

- 禁止跨服务共享数据库
- 禁止直接依赖他域内部模块
- 禁止用共享库替代上下文边界
- 禁止把业务判断写进 gateway 或协议层

## 4. 命名规范

### 4.1 服务命名

- 统一使用 `{domain}-service`

例如：

- `auth-service`
- `permission-service`
- `identity-service`

### 4.2 权限码命名

- 使用 `domain.resource.action`

例如：

- `inventory.stock.read`
- `procurement.order.approve`

### 4.3 命令与查询命名

- command 使用动词意图命名
- query 使用读取意图命名

### 4.4 事件命名

- 使用业务事实过去式语义

原因：

- 命名是多人协作时最基本的共识接口
- 命名不统一，后续文档、代码、事件、权限将全部混乱

## 5. 文档规则

项目级文档统一沉淀在：

- `docs/architecture`
- `docs/adr`
- `docs/plans`

旧的 `doc/standards` 与其他 `doc/` 文档目前可作为经验来源和过渡参考，但新的项目级架构设计不应继续分散沉淀。

文档职责：

- `index.md`：只做导航
- architecture 文档：稳定设计
- ADR：关键决策与取舍
- plans：路线图与阶段执行

### 5.1 编码规则

为保证多线程协作、终端读取、编辑器保存与后续自动化流程的一致性，项目统一采用以下编码规则：

- 所有新增与修改文件统一使用 `UTF-8`。
- 禁止继续新增 `GBK`、`ANSI` 或依赖本地系统默认编码的文件。
- 文档正文允许使用中文。
- 代码标识符、目录名、文件名、proto 字段、事件名、权限码统一使用英文。
- 若历史文档存在乱码，不能在乱码状态下继续扩写，应先标记并纳入转码修复范围。
- 如果线程读取历史文档时发现明显编码异常，应说明该文档存在编码风险，不能直接据此下架构结论。

### 5.2 语言规则

- 项目级设计文档、治理文档、计划文档可以使用中文。
- 为保持代码与契约的跨工具稳定性，程序内标识符统一使用英文。
- 重要术语在首次出现时可采用“中文术语 + 英文术语”并列表达。

## 6. ADR 决策记录规则

凡涉及以下内容，必须进入 ADR：

- bounded context 调整
- 新服务建立
- gRPC / proto 契约策略
- 事件模型
- 租户隔离模型
- IAM 模型
- scope / policy 模型
- `src/common` 对外公共抽象
- AI 工具协议
- operator context
- 数据一致性策略
- 审计模型

原因：

- 这些属于高影响、难回滚、跨模块的基础决策

## 7. 哪些内容必须先设计后编码

以下内容必须先完成设计，再进入实现：

- 新业务上下文建立
- 领域边界调整
- 平台级能力建立
- 公共契约变更
- 事件发布与消费规则
- 多租户数据边界
- 权限模型调整
- AI 接入方式与工具边界

## 8. 哪些改动属于跨模块改动

以下改动属于跨模块改动，不能由单个线程擅自决定：

- proto / 契约结构变更
- 公共异常码变更
- 权限含义调整
- 事件名称与字段调整
- operator context 结构变更
- 租户与组织模型变更
- `src/common` 对外 API 变更
- 审计字段标准变更
- AI 工具协议变更

## 9. 面向多个 Codex 线程的协作要求

每个 Codex 线程必须：

- 只拥有一个明确范围
- 明确自己的上游设计依据
- 明确哪些内容不归自己决策
- 优先在文档与 ADR 上建立一致性，再进入实现

推荐的线程类型：

- 架构治理线程
- 平台通信线程
- IAM 线程
- Tenant / Org 线程
- 观测与审计线程
- 业务域线程
- AI 平台线程

## 10. 与旧经验文档的继承关系

当前治理规则吸收并保留了旧 `doc/standards` 中以下有效经验：

- 文档分层职责清晰
- 单一事实源
- 最小闭环任务
- 设计与实现分离
- DDD / CQRS 分层纪律
- 服务模板化思路
- 分层测试思路

但在此基础上进一步补充了：

- 项目级系统上下文
- bounded context 统一边界
- AI 平台治理
- 租户与 IAM 平台化定位
- 多线程并行开发的全局一致性规则

## 11. 当前阶段治理结论

当前 OES 最需要治理的不是代码风格，而是：

- 边界
- 契约
- 权限
- 租户
- AI 接入方式
- 多线程协作纪律

这些是后续所有开发线程必须共同遵守的顶层约束。
