# OES 治理规则

> 涉及 permission-service 的服务职责、核心对象或 owner 边界时，以 [permission-service.md](/Users/acehood/Documents/GitHub/oes/docs/architecture/services/permission-service.md) 为准；本文只描述项目治理规则。

## 1. 治理目标

治理的目标不是增加流程，而是在多人、多线程、长期演进的前提下，让 OES 保持：

- 结构一致
- 边界清晰
- 责任明确
- 变更可控
- 设计可追踪

OES 是一个会持续扩大的企业级平台，没有治理就无法稳定演进。

## 2. 全项目统一设计原则

- 边界清晰优先于局部复用。
- 平台能力统一建设，业务能力领域化建设。
- 微服务拆分节制，避免过度拆分。
- 共享库只放通用能力，不放跨域业务逻辑。
- 所有跨模块协作都必须通过显式契约与文档表达。
- AI 增强必须服从业务边界与安全治理。

## 3. 模块间协作规则

### 3.1 协作方式

模块之间应通过以下方式协作：

- gRPC 契约
- 领域事件
- 防腐层
- 文档化的上下文关系

### 3.2 禁止事项

- 禁止跨服务共享数据库
- 禁止直接依赖他域内部模块
- 禁止用共享库替代上下文边界
- 禁止把业务判断写进 gateway 或协议层

## 4. 服务内部结构规则

服务内部应遵循项目根目录 `AGENTS.md` 中定义的分层职责，并额外注意以下工程边界：

- `modules/` 只负责依赖注入、provider 绑定、controller / handler 装配，不承载核心业务规则
- 业务能力依赖应在对应能力模块内装配，避免把所有仓储、handler、controller 堆入 `AppModule`
- `Mapper` 应作为 domain model 与 Prisma / persistence record / proto view model 之间的缓冲层
- 不应让 domain model 直接暴露数据库结构，也不应让 Prisma record 直接穿透到 application / interfaces 层
- repository interface 定义服务内持久化需求，repository implementation 与 mapper 负责消费具体持久化结构

## 5. 命名规范

### 5.1 服务命名

- 统一使用 `{domain}-service`

例如：

- `auth-service`
- `permission-service`
- `identity-service`

### 5.2 权限码命名

- 使用 `domain.resource.action`

例如：

- `inventory.stock.read`
- `procurement.order.approve`

### 5.3 命令与查询命名

- command 使用动词意图命名
- query 使用读取意图命名

### 5.4 事件命名

- 使用业务事实过去式语义

原因：

- 命名是多人协作时最基本的共识接口
- 命名不统一，后续文档、代码、事件、权限将全部混乱

## 6. 文档规则

项目级文档统一沉淀在：

- `docs/architecture`
- `docs/adr`
- `docs/plans`
- `docs/contracts`
- `docs/governance`

旧的根目录 `doc/` 不再作为项目级设计入口。历史经验已经收敛到 `AGENTS.md`、本治理文档与 `docs/governance/*`，后续不应继续新增或引用根目录 `doc/*` 作为当前设计依据。

文档职责：

- `index.md`：只做导航
- architecture 文档：稳定设计
- ADR：关键决策与取舍
- plans：路线图与阶段执行
- contracts：按服务 / 模块沉淀黑盒接口文档
- governance 文档：协作规则、文档归位、执行纪律与疑难 bug 根因知识库

### 6.1 编码规则

为保证多线程协作、终端读取、编辑器保存与后续自动化流程的一致性，项目统一采用以下编码规则：

- 所有新增与修改文件统一使用 `UTF-8`。
- 禁止继续新增 `GBK`、`ANSI` 或依赖本地系统默认编码的文件。
- 文档正文允许使用中文。
- 代码标识符、目录名、文件名、proto 字段、事件名、权限码统一使用英文。
- 若历史文档存在乱码，不能在乱码状态下继续扩写，应先标记并纳入转码修复范围。
- 如果线程读取历史文档时发现明显编码异常，应说明该文档存在编码风险，不能直接据此下架构结论。

### 6.2 语言规则

- 项目级设计文档、治理文档、计划文档可以使用中文。
- 为保持代码与契约的跨工具稳定性，程序内标识符统一使用英文。
- 重要术语在首次出现时可采用“中文术语 + 英文术语”并列表达。

### 6.3 接口文档规则

当一个服务或模块达到“可供其他模块依赖”的完成态后，必须同步提供接口文档。

目标：

- 让调用方把下游服务当作 black box 使用
- 让调用方优先通过接口文档理解能力，而不是阅读实现代码
- 让契约变更有稳定的阅读入口与审查入口

规则：

- 对外 HTTP 接口：
  - 优先使用 OpenAPI / Swagger
- 对内 gRPC / Event：
  - 不以 Swagger 作为主文档
  - 必须提供独立的黑盒接口文档
- 契约真相源仍然是：
  - HTTP 的 DTO / Controller / OpenAPI
  - gRPC 的 proto
  - Event 的事件契约定义
- 黑盒接口文档是面向人阅读的二级视图，不替代真相契约

推荐目录：

- `docs/contracts/<service-name>/`

推荐拆分粒度：

- 一个服务一份总览文档
- 每个稳定模块一份独立接口文档

每份接口文档至少应包含：

- 模块职责
- 开放接口清单
- 请求 / 响应摘要
- 调用前置条件
- 权限要求
- tenant / org / operator context 要求
- 关键错误语义
- 幂等性 / 副作用说明
- 上下游依赖关系

### 6.4 文档维护规则

项目文档应遵循单一事实源：

- 一个主题只能有一个当前主文档
- 其他文档只能引用主文档，不应重复展开同一正文
- 历史文档与归档文档不能替代当前有效设计

设计与实施应保持可追踪：

- 稳定设计写入 `docs/architecture/` 或服务内 `design/*.md`
- 阶段实施路径写入 `docs/plans/` 或服务内 `tasks/*.md`
- `design` 应说明对应实施入口；`tasks` 应回链上游设计
- `tasks` 默认按最小闭环切分，不把多个独立功能合并成一个大任务

链接与命名应保持跨环境可用：

- 仓库内文档链接优先使用相对路径
- 不在仓库文档中写本机绝对路径作为长期链接
- 文件名应按稳定主题命名，不使用“最终版”“完整方案”“优化版”等版本形容词

## 7. ADR 决策记录规则

凡涉及以下内容，必须进入 ADR：

- bounded context 调整
- 新服务建立
- gRPC / proto 契约策略
- 事件模型
- 租户隔离模型
- IAM 模型
- scope / policy 模型
- `src/common` 对外公共抽象
- AI 工具协议
- operator context
- 数据一致性策略
- 审计模型

原因：

- 这些属于高影响、难回滚、跨模块的基础决策

## 8. 哪些内容必须先设计后编码

以下内容必须先完成设计，再进入实现：

- 新业务上下文建立
- 领域边界调整
- 平台级能力建立
- 公共契约变更
- 事件发布与消费规则
- 多租户数据边界
- 权限模型调整
- AI 接入方式与工具边界

## 9. 哪些改动属于跨模块改动

以下改动属于跨模块改动，不能由单个线程擅自决定：

- proto / 契约结构变更
- 公共异常码变更
- 权限含义调整
- 事件名称与字段调整
- operator context 结构变更
- 租户与组织模型变更
- `src/common` 对外 API 变更
- 审计字段标准变更
- AI 工具协议变更

## 10. 面向多个 Codex 线程的协作要求

每个 Codex 线程必须：

- 只拥有一个明确范围
- 明确自己的上游设计依据
- 明确哪些内容不归自己决策
- 优先在文档与 ADR 上建立一致性，再进入实现

推荐的线程类型：

- 架构治理线程
- 平台通信线程
- IAM 线程
- Tenant / Org 线程
- 观测与审计线程
- 业务域线程
- AI 平台线程

## 11. 与旧经验文档的继承关系

当前治理规则已经吸收并保留了旧标准文档中的以下有效经验：

- 文档分层职责清晰
- 单一事实源
- 最小闭环任务
- 设计与实现分离
- DDD / CQRS 分层纪律
- 服务模板化思路
- 分层测试思路

但在此基础上进一步补充了：

- 项目级系统上下文
- bounded context 统一边界
- AI 平台治理
- 租户与 IAM 平台化定位
- 多线程并行开发的全局一致性规则

## 12. 当前阶段治理结论

当前 OES 最需要治理的不是代码风格，而是：

- 边界
- 契约
- 权限
- 租户
- AI 接入方式
- 多线程协作纪律

这些是后续所有开发线程必须共同遵守的顶层约束。
