# OES 服务协同规则

## 1. 文档目的

本文档用于冻结 OES 项目级服务协同规则，回答以下问题：

- 什么时候应使用同步 `gRPC`
- 什么时候应使用异步 `Event`
- 同一个 command 中如何组合“写前校验”和“写后事实扩散”
- 事件命名、payload 与长流程解耦应遵守什么边界

本文档是项目级稳定设计，服从以下上游约束：

- `AGENTS.md`
- `technical-architecture.md`
- `observability-and-audit.md`
- `grpc-metadata-and-service-trust.md`

## 2. 核心结论

OES 服务协同默认遵循以下分工：

- `gRPC`
  - 用于当前请求必须立刻拿到答案的内部同步协作。
- `Event`
  - 用于本服务状态已经成功改变之后的事实扩散与后续异步处理。

组合规则固定为：

1. 写入前强校验走 `gRPC`
2. 本地事务成功后再发布 `Event`
3. 不允许依赖 `Event` 完成本服务本地事务

## 3. `gRPC` 的适用场景

以下场景默认应使用 `gRPC`，而不是先发事件再等待别人补结果：

### 3.1 当前真相查询

适用：

- 当前请求需要读取别的服务“此刻”的 owner truth
- 调用方必须基于当前答案继续返回结果或继续执行 command

典型场景：

- 查询当前客户是否存在
- 查询当前物料是否处于可采用状态
- 查询当前组织、身份、权限或资源归属是否有效

### 3.2 外部对象存在性 / 状态校验

适用：

- 本服务写入前需要确认外部对象存在
- 本服务写入前需要确认外部对象当前状态允许本次操作

典型场景：

- 创建销售报价前确认 `party-service` 中客户存在
- 创建发货请求前确认销售单当前未取消
- 创建审批任务前确认目标对象仍处于可提交状态

### 3.3 当前 command 的前置条件

适用：

- 若拿不到下游答案，当前 command 就不能继续
- 若下游返回“不满足条件”，当前 command 必须立即失败或拒绝

典型场景：

- 权限与资源范围校验
- 幂等键或引用对象的硬前置校验
- 需要立即判定“允许 / 不允许”的同步门禁

### 3.4 API Gateway / BFF 聚合查询

适用：

- 外部客户端需要一个同步聚合结果
- `api-gateway` / BFF 需要面向页面或 API 组装多个下游的当前读模型

约束：

- 聚合层只负责编排和协议适配
- 不得在聚合层沉淀跨域 owner truth
- 不得把聚合查询偷换成跨域业务规则真相

### 3.5 明确同步的内部命令

适用：

- 上游必须知道下游至少已经“受理 / 拒绝”
- 下游同步处理结果本身就是当前请求的一部分

典型场景：

- 需要即时确认平台是否接受某个内部命令
- 上游若拿不到受理结果，就无法给调用方返回明确结论

补充约束：

- 同步命令只表示“当前请求要拿到结果”，不表示跨服务长事务
- 若后续步骤天然可延迟或可重试，应在下游服务内部异步推进

## 4. `Event` 的适用场景

以下场景默认应使用 `Event`，而不是同步要求所有消费者立即完成：

### 4.1 本服务状态已成功改变后的事实扩散

适用：

- 本服务已经完成本地状态变更
- 其他服务只是需要知道“发生了什么”

核心要求：

- 先有本地成功事实，再有对外事件
- 事件表达的是已发生事实，不是希望别人去执行的命令

### 4.2 读模型更新

适用：

- 下游只是在维护自己的 projection、cache 或查询视图
- 下游失败不应反过来否定源服务刚刚成功的本地事务

### 4.3 Notification

适用：

- 大多数业务通知、提醒、状态广播
- 平台只需要消费业务事实并决定是否发送、发给谁、用什么模板

说明：

- 是否需要“同步受理”是 `gRPC` 问题
- 真正通知投递与重试属于事件驱动或平台内部异步处理问题

### 4.4 `ObjectActivity` / `Timeline`

适用：

- 业务对象已经产生值得协作者阅读的活动事实
- 下游只是在构建时间线、活动流或相关协作读模型

约束：

- activity / timeline 是读模型协同，不是源对象写入真相

### 4.5 `BI` / `Analytics`

适用：

- 数仓、统计、副本分析、报表口径衍生
- 下游消费的是业务事实，而不是参与当前事务提交

### 4.6 Search Index

适用：

- 搜索索引刷新
- 检索侧快照更新

约束：

- 不允许为了等索引完成而阻塞源服务本地事务

### 4.7 Cache Invalidation

适用：

- 缓存失效、重建、派生数据刷新

约束：

- cache 是衍生层，不是 owner truth
- 不能反过来要求源事务为缓存结果负责

### 4.8 长流程解耦

适用：

- 一个业务动作完成后，还会触发多个下游异步阶段
- 这些阶段不应被串成同步长链路

说明：

- 事件用于切换阶段、解耦消费者和隔离失败域
- 长流程状态协调应由 future workflow / process manager / event-driven coordination 承接

## 5. 组合规则

### 5.1 写入前强校验用 `gRPC`

- 只要当前 command 需要当前答案，默认走 `gRPC`
- 不允许把“写前硬校验”改写成“先发事件，等别人异步告诉我能不能做”

### 5.2 本地事务成功后发布 `Event`

- 只有本地事务已经成功，才允许向外发布事实事件
- 事件的职责是通知别的服务“这个事实已经成立”

### 5.3 不允许依赖 `Event` 完成本服务本地事务

明确禁止：

- 先发事件，再等消费者回写，最后才算本地事务成功
- 依赖异步消费者补齐当前 command 的本地必填真相
- 把本地事务拆散到多个服务上形成隐式分布式事务

## 6. 命名规则

### 6.1 事件必须是过去式事实

事件名必须表达“已经发生”的业务事实，例如：

- `InvoiceCreated`
- `SalesOrderReleased`
- `CustomerApproved`
- `ItemStatusChanged`

### 6.2 不允许命令式事件名

以下命名属于禁止项：

- `CreateInvoice`
- `NotifyFinance`
- `SyncCustomer`

原因：

- 命令式事件会把“事实扩散”和“命令下达”混在一起
- 会让消费者误以为自己必须执行某个动作，导致跨服务耦合升级

## 7. Payload 规则

### 7.1 事件只携带最小必要信息

事件 payload 应优先只包含：

- 稳定 ID
- 必要快照
- `tenant` context
- `operator` context
- `trace` context
- 必要审计元数据

### 7.2 不复制完整 owner truth

明确禁止：

- 把 owner 服务完整主数据塞进事件 payload
- 让消费者长期依赖事件中的大对象快照代替 owner truth
- 用事件复制下游本可通过受控查询获得的整套内部结构

说明：

- 必要快照只服务于解耦、审计归因、读模型更新或搜索索引等明确场景
- 快照不是 owner truth 转移

### 7.3 上下文传播要求

所有服务协同都必须显式携带并传播适用上下文：

- `tenantId`
- `orgId`，如果场景适用
- `operator context`
- `trace context`
- 必要审计元数据

详细的 `gRPC metadata` 传播规则，以 [grpc-metadata-and-service-trust.md](../platforms/grpc-metadata-and-service-trust.md) 为准。

## 8. 长流程规则

### 8.1 不要串联多个 `gRPC` 调用形成跨服务长事务

明确禁止：

- 把多个服务同步串联成“全部成功才算成功”的长调用链
- 用层层同步调用模拟分布式事务
- 让某个 command 在多个服务之间来回阻塞等待

### 8.2 Future 统一承接方式

未来涉及跨服务长流程时，应优先由以下机制承接：

- workflow
- process manager
- event-driven coordination

本文只冻结协同边界，不在本线程展开以下实现决策：

- 选择哪一种 event broker
- 是否以及如何实现 outbox
- 具体 workflow runtime 选型

## 9. 审查判定口径

遇到一个新的跨服务调用或事件设计时，先问：

1. 当前请求是否必须立刻拿到答案
2. 若下游失败，当前 command 是否必须失败
3. 这是同步校验，还是写后事实扩散
4. 是否存在多个消费者
5. 该需求是否主要服务于读模型、通知、activity、BI、搜索或缓存

默认判定：

- 需要当前答案、需要立刻失败闭环：优先 `gRPC`
- 源服务已成功、只需扩散给一个或多个消费者：优先 `Event`

审查时直接核对本文件的 owner、调用方向、失败语义、幂等、审计与一致性约束。

## 10. 非目标

本文明确不负责：

- 审查现有仓库里的全部调用与全部事件
- 迁移现有服务调用
- 选择 `Kafka / RabbitMQ / NATS`
- 设计或实现 outbox / event bus
- 设计审计模型本身
- 替代单个协同蓝图、单个服务职责卡或具体契约正文
