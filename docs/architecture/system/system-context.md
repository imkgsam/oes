# OES 系统上下文

## 1. 系统上下文定位

OES 位于企业内部经营与制造协同的中枢位置。

它向上承接：

- Web 管理端
- 移动端
- PDA / 现场终端
- 外部客户、供应商与合作方访问入口
- 外部 Ecom 渠道
- IM / Email 渠道

它向下连接：

- 业务域服务
- 平台服务
- 企业内部基础设施
- 外部第三方系统
- 外部模型与知识来源

因此，OES 的系统上下文不是单一应用，而是企业数字运营与智能协同平台。

## 2. 外部参与方

OES 面对的外部参与方包括：

- 企业内部操作员
- 管理者与决策者
- 销售、采购、仓储、生产、计划等业务岗位
- 客户与供应商
- 第三方电商平台
- 第三方物流、财务、IoT、设备系统
- IM 与 Email 服务提供方
- 外部大模型与 AI 能力提供方

识别这些外部参与方的原因是，不同参与方决定了不同的认证方式、权限边界、数据边界与集成模式。

## 3. 系统边界

### 3.1 OES 系统内部

OES 内部包括：

- 业务域服务
- 身份与权限平台
- 主数据与主体抽象
- 工作流与任务编排
- 通知与消息处理
- 审计与可观测平台
- AI 平台与知识平台
- 对外集成与连接器

### 3.2 OES 系统外部

OES 外部包括：

- 第三方业务系统
- 第三方基础设施服务
- 外部沟通渠道
- 外部模型服务
- 人工审批与管理动作

这个边界的关键意义在于：

- OES 对内部业务语义负责
- 对外部系统只通过显式契约集成
- 不允许外部系统的语义直接污染 OES 内部领域模型

## 4. 分层视角下的系统上下文

### 4.1 体验层

负责面向不同角色和终端提供交互入口，包括：

- Web
- Mobile
- PDA
- 外部 Partner 接入
- BFF / API Gateway

### 4.2 平台层

负责承载统一能力，包括：

- IAM
- Tenant / Org
- Workflow
- Notification
- Integration
- Audit
- Knowledge & AI

### 4.3 业务层

负责承载企业实际经营与制造逻辑，包括：

- ERP
- MES
- WMS
- CRM
- SRM
- APS
- CMS
- BI
- Ecom

### 4.4 基础设施层

负责承载支撑技术能力，包括：

- Config
- Registry
- Event Bus
- Logging
- Tracing
- Metrics
- Scheduling
- Search
- Storage

## 5. 系统交互原则

- 外部访问统一经过 Gateway / BFF。
- 内部同步调用使用强契约机制。
- 跨上下文传播优先使用事件而不是共享内部状态。
- AI 能力不能直接越过平台层访问业务核心。
- 审计链与 trace 链应贯穿从入口到执行的全过程。

## 6. 当前阶段的上下文结论

当前 OES 不应被理解为“正在做几个 system service”，而应被理解为：

- 已经启动了平台底座建设
- 下一步要在清晰上下文约束下逐步接入业务域
- 所有业务域与 AI 能力都必须建立在这一上下文边界之上

如果没有这一系统上下文约束，后续实现会自然滑向：

- 业务边界混乱
- 平台能力重复实现
- AI 无边界接入
- 微服务数量失控
