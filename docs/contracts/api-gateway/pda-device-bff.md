# PDA Device BFF Contract

> PDA BFF 只聚合设备端启动所需信息，不拥有 terminal access、access summary、角色、权限或导航授权真相；这些服务设计边界以 [permission-service.md](../../architecture/services/permission-service.md) 为准。

## 1. Purpose

This document defines the Phase 1 PDA device and bootstrap HTTP contracts exposed by API Gateway / BFF.

These contracts support the PDA system foundation only:

- session bootstrap
- device heartbeat
- manual diagnostic log upload

They do not define WMS / MES business workflows, offline submission, device management UI, file upload, or photo attachment semantics.

## 2. Boundary

The PDA BFF owns the external HTTP shape consumed by the PDA terminal.

It does not own:

- authentication truth
- identity truth
- permission truth
- terminal access truth
- device registry truth
- WMS / MES business truth
- attachment storage truth

The PDA BFF may aggregate downstream services and normalize PDA device metadata, but it must not embed core business rules.

## 3. Common Request Context

PDA requests should carry the normal Gateway request context plus PDA device metadata when available.

Recommended device metadata shape:

```json
{
  "deviceId": "SEUIC-SN-123456",
  "idSource": "MANUFACTURER_SERIAL",
  "fallbackAppDeviceId": "app-uuid-xxx",
  "manufacturer": "Seuic",
  "deviceModel": "Cruise Ge",
  "androidVersion": "9",
  "appVersion": "1.0.0"
}
```

`idSource` values:

| Value | Meaning |
| --- | --- |
| `MANUFACTURER_SERIAL` | Device id was read from the PDA manufacturer / Android device identifier. |
| `APP_GENERATED` | Device id was generated by the OES PDA App because manufacturer id was unavailable or unreliable. |

Phase 1 should prefer a stable manufacturer identifier when available and fall back to an App-generated id.

## 4. `GET /pda/session/bootstrap`

### 4.1 Purpose

Initializes the PDA terminal after login or after a session restore attempt.

This endpoint returns the current session/account summary, permission access summary, device status, device policy, version policy, workbench configuration, and server time in one PDA-friendly response.

### 4.2 Users

Authenticated PDA users.

### 4.3 Control Model

- Requires a valid PDA session.
- Terminal must resolve as `PDA`.
- Terminal Access Policy is enforced by the login / refresh path, not by frontend-only checks.

### 4.4 Response

```json
{
  "account": {
    "accountId": "acc_001",
    "tenantId": "tenant_001",
    "scopeLevel": "TENANT",
    "displayName": "Zhang San"
  },
  "session": {
    "sessionId": "sess_001",
    "terminal": "PDA",
    "expiresAt": "2026-05-13T18:00:00Z",
    "idleTimeoutSeconds": 900
  },
  "access": {
    "roles": [],
    "actionCodes": []
  },
  "device": {
    "deviceStatus": "ACTIVE",
    "deviceId": "SEUIC-SN-123456",
    "idSource": "MANUFACTURER_SERIAL"
  },
  "devicePolicy": {
    "heartbeatIntervalSeconds": 300,
    "idleTimeoutSeconds": 900,
    "minSupportedAppVersion": "1.0.0",
    "latestAppVersion": "1.0.0",
    "upgradeRequired": false
  },
  "workbench": {
    "mode": "FOUNDATION_ACCEPTANCE",
    "enabledCards": [
      "SESSION",
      "DEVICE",
      "NETWORK",
      "SCAN",
      "CAMERA",
      "LOGS"
    ]
  },
  "serverTime": "2026-05-13T10:00:00Z"
}
```

### 4.5 Phase 1 Rules

- `workbench.mode` is fixed to `FOUNDATION_ACCEPTANCE`.
- The response must not return WMS / MES business tasks.
- `deviceStatus` is reserved for future device management and may be fixed to `ACTIVE` in Phase 1.
- `devicePolicy` may return fixed default values in Phase 1.
- `access` is an aggregate of permission-service access summary, not a PDA-owned permission truth.

## 5. `POST /pda/device/heartbeat`

### 5.1 Purpose

Records the latest PDA device / App runtime state for diagnostics and future device management.

Heartbeat is about PDA App / device activity. It is not the source of user login truth.

### 5.2 Users

PDA App before or after login.

### 5.3 Control Model

- May be accepted before login.
- If authenticated, the request may include session summary.
- Phase 1 stores only the latest known state.
- Phase 1 does not expose a device management UI.
- Phase 1 does not implement device disablement.

### 5.4 Request

```json
{
  "device": {
    "deviceId": "SEUIC-SN-123456",
    "idSource": "MANUFACTURER_SERIAL",
    "fallbackAppDeviceId": "app-uuid-xxx",
    "manufacturer": "Seuic",
    "deviceModel": "Cruise Ge",
    "androidVersion": "9",
    "appVersion": "1.0.0"
  },
  "runtime": {
    "networkStatus": "ONLINE",
    "batteryLevel": 72,
    "appState": "FOREGROUND"
  },
  "session": {
    "accountId": "acc_001",
    "tenantId": "tenant_001",
    "sessionId": "sess_001"
  },
  "clientTime": "2026-05-13T10:10:00Z"
}
```

`session` may be `null` when the App has not logged in:

```json
{
  "session": null
}
```

### 5.5 Response

```json
{
  "accepted": true,
  "deviceStatus": "ACTIVE",
  "devicePolicy": {
    "heartbeatIntervalSeconds": 300,
    "idleTimeoutSeconds": 900,
    "minSupportedAppVersion": "1.0.0",
    "latestAppVersion": "1.0.0",
    "upgradeRequired": false
  },
  "serverTime": "2026-05-13T10:10:03Z"
}
```

### 5.6 Phase 1 Stored State

Phase 1 should persist or otherwise retain the latest state needed for diagnostics:

- `deviceId`
- `idSource`
- `fallbackAppDeviceId`
- `manufacturer`
- `deviceModel`
- `androidVersion`
- `appVersion`
- `networkStatus`
- `batteryLevel`
- `appState`
- `accountId`, nullable
- `tenantId`, nullable
- `sessionId`, nullable
- `lastHeartbeatAt`
- `lastClientTime`

## 6. `POST /pda/device/logs`

### 6.1 Purpose

Uploads PDA diagnostic logs manually triggered from the PDA App.

This endpoint is for Phase 1 field diagnostics. It is not a general log platform and does not replace observability or audit architecture.

Phase 2 persists sanitized accepted logs in `terminal-device-service`; any gateway-local buffer is only a convenience cache and is not admin history truth.

### 6.2 Users

PDA App before or after login.

### 6.3 Control Model

- May be accepted before login.
- Upload is manual in Phase 1.
- Automatic background upload is not part of Phase 1.
- Logs must not contain passwords, access tokens, refresh tokens, photo file content, or full business documents.

### 6.4 Request

```json
{
  "device": {
    "deviceId": "SEUIC-SN-123456",
    "idSource": "MANUFACTURER_SERIAL",
    "manufacturer": "Seuic",
    "deviceModel": "Cruise Ge",
    "androidVersion": "9",
    "appVersion": "1.0.0"
  },
  "session": {
    "accountId": "acc_001",
    "tenantId": "tenant_001",
    "sessionId": "sess_001"
  },
  "logs": [
    {
      "clientTime": "2026-05-13T10:15:00Z",
      "level": "INFO",
      "eventType": "SCAN_RECEIVED",
      "message": "Scan result received",
      "traceId": "trace_001",
      "requestId": "req_001",
      "errorCode": null,
      "diagnosticMode": true,
      "details": {
        "scanValue": "PB202605130001",
        "scanLength": 14,
        "scanSource": "BROADCAST"
      }
    },
    {
      "clientTime": "2026-05-13T10:16:00Z",
      "level": "ERROR",
      "eventType": "BRIDGE_CALL_FAILED",
      "message": "openCamera failed",
      "traceId": "trace_002",
      "requestId": null,
      "errorCode": "CAMERA_PERMISSION_DENIED",
      "diagnosticMode": true,
      "details": {
        "bridgeMethod": "openCamera"
      }
    }
  ]
}
```

`session` may be `null` when the App has not logged in.

### 6.5 Response

```json
{
  "accepted": true,
  "receivedCount": 2,
  "serverTime": "2026-05-13T10:16:03Z"
}
```

### 6.6 Diagnostic Scan Values

Phase 1 diagnostic uploads may include full `scanValue` because scan debugging needs to detect:

- missing characters
- unexpected prefix / suffix
- encoding issues
- wrong scanner source
- wrong scan ordering

Rules:

- Uploading full `scanValue` is allowed only for manual diagnostic logs in Phase 1.
- Events carrying full `scanValue` must set `diagnosticMode = true`.
- Future business logs must not automatically upload full business scan values unless a user manually triggers diagnostic upload.

## 7. Deferred Work

- Device list / detail management UI.
- Device disablement.
- Device binding / grouping.
- Device online dashboard.
- MDM / enterprise device management.
- Automatic log upload.
- General file or photo upload.
- WMS / MES business scan contracts.

## 8. Managed device credential and trusted downstream calls

Enrollment activation returns a one-time `deviceCredential`, `deviceCredentialExpiresAt` and `deviceCredentialVersion` in addition to `terminalDeviceId`. The default lifetime is 30 days. The Android shell encrypts it with Android Keystore and never exposes it to Vue logs, URL/query, analytics, crash reports or ordinary storage. Heartbeat rotates it when seven days or less remain; old/new values overlap for at most five minutes. Subsequent `/pda/device/heartbeat`, `/pda/device/logs`, `/pda/session/bootstrap` and PDA login device checks send it in the dedicated HTTPS header `X-OES-Terminal-Device-Credential`; it is absent from JSON DTOs and API responses after activation.

Gateway treats this value as an opaque Terminal Device Service credential. It does not validate it locally, persist it, map it to a HUMAN/MACHINE principal, put it in ordinary gRPC metadata or use it as an Auth STS source credential. Gateway forwards it only in the exact terminal-device proto field of `ResolveDeviceAccessDecision`, `RecordHeartbeat` or `RecordDiagnosticLogs`, after request logging/redaction has excluded the value.

The four PDA-side downstream methods are INTERNAL calls made with the existing Gateway SYSTEM MACHINE root:

- `ActivateEnrollment -> terminal-device.internal.gateway.enrollment.activate`;
- `ResolveDeviceAccessDecision -> terminal-device.internal.gateway.access.resolve`;
- `RecordHeartbeat -> terminal-device.internal.gateway.heartbeat.record`;
- `RecordDiagnosticLogs -> terminal-device.internal.gateway.diagnostic_log.record`.

All use `aud=urn:oes:service:terminal-device-service`, the exact Gateway SPIFFE workload, current mTLS leaf binding and the existing process-local ET cache. This remains true when an optional PDA HUMAN session exists: session facts can be attached only as reported diagnostics or used by the separate Auth/bootstrap aggregation, and never switch these four Terminal Device RPCs to HUMAN.

Missing/invalid/suspended/revoked device credential fails closed. Device credential proves only possession of the enrolled PDA secret; it grants no WMS/MES/business or Admin permission. Marking the device unavailable still returns the existing cleanup decision; Redis `terminal-device.unavailable` remains a separate async session-cleanup path.
